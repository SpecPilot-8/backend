# 참고 코드만 있는 판정의 저장 실패 수정

## 실제 관측과 재현 범위

2026-10-30 로컬 검증 실행 `7c1fb13b-f52d-4091-9080-8f14a8875f56`는 103개 요구사항 중 35개를 저장하고 `MODEL_OUTPUT_INVALID`로 종료됐다. 첫 미저장 대상은 `NOTICE-001-1`(공지사항 목록 Description 1)이다. 이후 실행은 사용자 취소로 종료됐으며 별개의 사건이다.

실제 실패 시 판정 초안과 세부 위반 규칙을 저장하지 않았으므로, 그 실행의 어느 조건이 어떤 검사를 위반했는지 사후 확정할 수는 없다. 다만 현재 실행기에서 동일 오류를 발생시키는 아래 계약 충돌을 LLM 없는 통합 테스트로 재현했다.

## 충돌과 수정

모델이 조건을 `not_found`로 판정하고 `evidence_chunk_ids`를 비워도, 실행기는 매칭에서 선택한 다른 화면 코드를 참고 근거로 붙일 수 있다. 저장 어댑터는 주 근거 없이 참고 근거만 있는 경우 `needs_review` 또는 `not_statically_verifiable`만 허용한다. 따라서 다음 조합이 전체 Job을 실패시켰다.

```text
status = not_found
primary_chunk_ids = []
reference_chunk_ids = [유효한 다른 화면 청크]
```

실행기가 이 조합을 `needs_review`로 정리하고, 해당 화면 근거는 없으며 다른 화면의 참고 코드만 있어 검토가 필요하다는 사유와 기존 모델 설명을 보존하도록 했다. 다른 화면 근거는 `other_screen`을 유지한다. 저장 어댑터의 거절 규칙은 그대로 두어 잘못된 결과가 직접 들어오면 계속 거절한다.

| 입력 상황 | 저장할 상태 |
| --- | --- |
| 미구현 판정, 주 근거 없음, 참고 근거 있음 | 검토 필요 |
| 미구현 판정, 주·참고 근거 모두 없음 | 미구현 후보 유지 |
| 미구현 판정, 주 근거 있음 | 미구현 후보와 근거 유지 |
| 정적 검증 불가 조건 | 정적 검증 불가 유지 |

판정 정책 변경을 추적하도록 `RULES_VERSION`을 `scope-static-v1-filter-3/aggregate-v1`로 올렸다. 모델 입력 프롬프트는 바꾸지 않았다.

## 다음 오류를 추적하기 위한 기록

저장 검사는 `output_schema`, `condition_coverage`, `primary_scope`, `reference_only_status` 등 규칙 식별자를 제공한다. 가능한 경우 서버에 존재하는 요구사항 ID와 조건 ID를 함께 남긴다. 실행기는 이 식별 정보만 Job과 검증 실행의 `error.details`로 보존한다. 모델 응답 전체, 원문 코드, 외부 제공자의 예외 본문은 추가하지 않는다.

예:

```json
{
  "code": "MODEL_OUTPUT_INVALID",
  "details": {
    "rule": "reference_only_status",
    "requirement_id": "저장된 요구사항 ID",
    "condition_id": "저장된 조건 ID"
  }
}
```

## 검증

- 수정 전 새 테스트에서 참고 코드만 있는 미구현 판정의 Job 실패와 오류 상세 정보 누락을 확인했다.
- 수정 후 관련 통합 테스트 28개, 전체 pytest 182개와 변경 파일 Ruff 검사가 통과했다.
- 새 회귀 사례는 참고 코드만 있음, 근거 모두 없음, 주 근거 있음, 어댑터의 잘못된 상태 거절 유지, 두 번째 요구사항 저장 실패 시 첫 결과 보존과 오류 식별 정보 보존을 검사한다.
- 외부 LLM 호출 없이 별도 테스트 DB와 가짜 모델 응답을 사용했다. 실제 103개 요구사항의 유료 재검증과 판정 정확도 평가는 수행하지 않았다.

기존 실패 실행과 완료한 35개 결과는 수정하지 않는다. 현재 새 검증 실행은 이전 실행의 나머지를 자동 재개하지 않으므로 재검증에는 모델 호출이 다시 필요하다.
