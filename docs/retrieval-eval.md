# 검색(RAG) 후보 축소 측정

코드가 LLM 컨텍스트를 넘을 때 쓸 후보 축소 단계를 만들고, 정답 근거를 얼마나 남기는지 쟀다. 2026-10-26.
판정 파이프라인에는 아직 연결하지 않았다. 지금 매칭은 레포 전체 청크를 후보로 넣는다(full_context).

## 결론

- **화면 범위 안에서 로컬 임베딩(BGE-M3)으로 검색하면 상위 30개로 판정 근거의 약 90%(Spring)·94%(React)를 남긴다.**
  상위 50개면 96%·98%다. 화면 범위 평균(Spring 90개, React 56개)보다 후보가 줄어든다
- **키워드 검색(BM25)만으로는 부족하다.** 상위 30개로 66%·83%다. 기획서는 한국어, 코드는 영어 식별자라 단어가 덜 겹친다
- **BM25와 임베딩을 섞어도(RRF) 나아지지 않았다.** K ≥ 20에서 임베딩 단독보다 2~4%p 낮다. 섞는 방식(가중치)을 바꾸면 달라질 수 있다
- **화면 범위가 먼저다.** 같은 임베딩이라도 레포 전체에서 검색하면 상위 30개로 62%·74%로 떨어진다

## 방법

`python scripts/eval_retrieval.py` (LLM 호출 없음, 두 레포 약 1분. 임베딩은 `output/embeddings/`에 캐시)

- 질의: 요구사항 본문 + 분해한 조건 문장. 청크: 파일 경로·심볼 이름 + 코드 본문 (`matcher/retrieve.py`)
- BM25: 영문 식별자는 camelCase로 나누고, 숫자는 그대로, 한글은 2-gram (PDF 추출에서 띄어쓰기가 사라짐)
- 임베딩: `BAAI/bge-m3`, 로컬 실행 (코드가 외부로 나가지 않음). 최대 4096토큰이라 긴 컴포넌트 청크도 잘리지 않는다
- 정답 근거
  - 판정 근거: 최근 전체 판정(Spring 13, React 14)에서 판정 LLM이 고른 primary 근거
  - 매칭 근거: 매칭 LLM이 레포 전체에서 고른 근거(다른 화면 코드 포함)
- Recall@K = 요구사항별 (정답 ∩ 상위 K) / 정답의 평균. 근거가 없는 요구사항은 뺀다

## 결과 (판정 근거 Recall@K)

| K | 범위 BM25 | 범위 임베딩 | 범위 혼합 | 전체 임베딩 |
|---|---|---|---|---|
| Spring 10 | 53.2% | 61.1% | 59.9% | 38.2% |
| Spring 20 | 60.9% | 82.2% | 78.4% | 54.8% |
| Spring 30 | 65.6% | **89.7%** | 86.9% | 62.4% |
| Spring 50 | 77.5% | **95.6%** | 94.7% | 75.4% |
| React 10 | 61.3% | 66.0% | 67.5% | 46.9% |
| React 20 | 72.9% | 85.2% | 81.5% | 68.0% |
| React 30 | 83.3% | **94.1%** | 90.6% | 74.4% |
| React 50 | 92.3% | **98.2%** | 97.8% | 86.9% |

화면 범위 전체를 넣으면 판정 근거는 100%(판정이 이 화면 근거에서만 고르므로), 매칭 근거는 Spring 84.9%·React 89.6%다.
매칭 근거 중 빠지는 것은 대부분 다른 화면 코드로, 화면 범위가 일부러 빼는 것이다. 매칭 근거 기준 전체 표는 스크립트 출력에 있다.

## 한계

- **정답이 LLM이 고른 근거다.** 판정 근거는 전체 코드를 본 매칭 결과에서 출발했다. 사람이 고른 근거가 아니다
- **샘플이 작다.** 청크 304개·139개라 화면 범위 자체가 작다. 큰 코드에서 K를 얼마로 할지는 다시 재야 한다
- **검색 Recall은 판정 정확도가 아니다.** 실제로 판정에 연결해 골든셋 정확도(현재 82~84%)가 유지되는지가 최종 기준이다.
  이 단계는 판정 LLM을 다시 돌려야 해서 비용이 든다
- Contextual Retrieval(청크마다 LLM이 맥락 설명을 붙여 색인)은 비용 때문에 넣지 않았다. 지금은 파일 경로·심볼 이름만 붙인다

## 다음

1. 판정 파이프라인에 연결: 화면 범위 → 요구사항별 상위 K(30~50) → 기존 선택·판정. 골든셋으로 정확도 비교
2. 로컬 LLM 전환 때 기본값으로 검토. 컨텍스트가 짧은 모델에서는 화면 범위도 다 안 들어갈 수 있다
3. 혼합 가중치, 리랭커는 상위 K에 정답이 자주 빠질 때 다시 본다

설치: 임베딩은 선택 기능이다. `pip install sentence-transformers` (torch 포함, 모델 약 2.2GB는 첫 실행 때 받음).
없으면 `--no-dense`로 BM25만 잰다.

## 임베딩 모델 비교 (2026-11-13, #109)

`python scripts/compare_embeddings.py` (LLM 호출 없음). 같은 조건: 화면 범위 안 검색, 질의는 요구사항 본문 + 분해 조건,
정답은 판정 13·14가 고른 primary 근거. 색인 시간은 Apple M5(24GB) CPU/MPS 기준, 캐시 없이 처음부터.

| 모델 | Spring R@10 / 30 / 50 | React R@10 / 30 / 50 | 색인(초) S / R | 최대 입력 |
|---|---|---|---|---|
| BGE-M3 (기존) | 61.1 / **89.7** / 95.6 | 66.0 / 94.1 / 98.2 | 14.7 / 10.3 | 8192 (4096 사용) |
| KURE-v1 (BGE-M3 한국어 추가 학습) | 58.4 / 88.3 / 94.3 | 72.8 / 94.8 / 98.0 | 11.4 / 9.9 | 8192 (4096 사용) |
| multilingual-e5-large | 58.4 / 86.0 / 94.4 | 55.3 / 89.5 / 98.6 | 11.0 / 7.5 | **512** |
| **Qwen3-Embedding-0.6B** | **63.0** / 89.3 / **96.3** | **78.6 / 97.1 / 100.0** | **8.1 / 5.9** | 32768 (4096 사용) |

- **Qwen3-Embedding-0.6B를 기본값으로 정했다.** React에서 확실히 앞서고(R@30 97.1% vs 94.1%), Spring은 BGE-M3와 같은 수준이다
  (R@30 차이 0.4%p는 요구사항 100개 중 1개 미만의 차이). 파라미터가 가장 작아 색인도 가장 빠르다.
- e5는 512토큰에서 잘려 긴 컴포넌트·템플릿 청크를 다 보지 못한다. 한국어 특화(KURE)는 영어 코드가 섞인 이 작업에서 이점이 없었다.
- 한계: 정답이 LLM이 고른 근거이고 표본이 레포 2개·요구사항 약 100개다. 모델 간 1~2%p 차이는 우연일 수 있다.

## 매칭 입력·비용 추정 (2026-11-13)

`python scripts/measure_retrieval_cost.py --model qwen3-0.6b`. 매칭 후보 = 화면의 요구사항마다 상위 K개의 합집합.
토큰은 기존 full_context 실행(match_call.usage)의 캐시 토큰으로 글자당 토큰을 보정해 추정했다 (실제 호출 아님).

| | 화면당 후보 | 매칭 입력 토큰 (12화면) | 판정 근거 유지 | 추정 매칭 비용 |
|---|---|---|---|---|
| Spring 전체 코드 (현재) | 304 | 650,664 | 100% | $0.64 |
| Spring 검색 30 | 55 | 126,720 (-81%) | 96.9% | $0.63 |
| React 전체 코드 (현재) | 139 | 450,192 | 100% | $0.44 |
| React 검색 30 | 41 | 123,523 (-73%) | 100% | $0.62 |

- **입력 토큰은 70~80% 줄지만 현재 규모에서 비용은 줄지 않는다.** 전체 코드 방식은 모든 화면이 같은 목록을 보내 두 번째 화면부터
  캐시(0.1배 단가)로 읽는다. 검색 방식은 화면마다 후보가 달라 캐시를 쓰지 못한다.
- 매칭은 판정 1회 비용의 약 15%다. 비용 대부분은 판정 단계 출력 토큰이다 (Spring 판정 $2.91 중 출력 $1.80).
- 이 단계의 이점은 비용보다 규모다. 전체 코드 방식의 입력은 레포 크기에 비례해 커지고(Spring 4천 줄에서 화면당 5.4만 토큰),
  검색 방식은 요구사항 수 × K에 묶인다. 문맥이 짧은 모델이나 큰 레포에서 차이가 난다.
- 판정 정확도가 유지되는지는 아직 재지 않았다 (`python scripts/run_match.py retrieval <repo>` 후 판정·골든셋 채점, API 비용 발생).

## 판정 정확도 확인 (2026-11-13, API 사용)

Spring 2개 화면(NOTICE-002, LOGIN-001, 조건 54개)만 검색 방식으로 다시 매칭·판정해 골든셋과 비교했다.
`run_match.py retrieval spring-sample --screens NOTICE-002 LOGIN-001 --top-k 30` → match run 6, `tag_scope.py --run 6`,
`run_verdict.py --match-run 6 --decompose-run 4` → verdict run 15. 같은 조건의 기존 판정(run 13, 전체 코드)과 비교.

| | 기존 (전체 코드) | 검색 30 (Qwen3) |
|---|---|---|
| 판정 시도 47개 중 일치 | 36 (77%) | 37 (79%) |
| 실제 결함 19개 중 잡음 | 15 | 14 |
| 결함을 implemented로 통과 | 2 | 2 |
| 정상 28개 중 오탐 | 2 | 0 |
| 매칭 후보 (화면당) | 304 | 61 / 43 |

- **정확도는 유지되었다.** 바뀐 판정 7개 중 맞게 바뀐 것 4, 틀리게 바뀐 것 3이다. 같은 정책을 다시 돌려도 판정의 약 14%가 바뀌므로
  (README 진행 상태) 이 차이는 흔들림 범위 안이다.
- 틀리게 바뀐 3개는 모두 needs_review로 갔다(사람 검토). 결함을 implemented로 통과시킨 수는 늘지 않았다.
- 소셜 로그인(LOGIN-001-1, 버튼만 있고 동작 없음)은 partial → needs_review로 바뀌었다. 어느 쪽이든 implemented로 오판하지는 않았다.
- 실제 매칭 비용은 화면 2개에 약 $0.17이었다. 클라이언트가 공유 문맥에 캐시 쓰기(1.25배)를 걸어 둬서, 추정($5/백만)보다 조금 비싸다.
  같은 2개 화면의 기존 매칭은 다른 화면이 데워 둔 캐시를 읽어 약 $0.09였다. **현재 규모에서는 검색이 비용을 줄이지 않는다는 추정이 실측으로도 맞았다.**
- 판정 단계 비용은 약 $0.67(출력 토큰이 $0.44)로 매칭보다 훨씬 크다. 이번 실행 전체 비용은 약 $0.83이다.
- 한계: 화면 2개, 1회 실행이다. 정확도 유지를 주장하려면 전체 화면과 반복 실행이 필요하다.
