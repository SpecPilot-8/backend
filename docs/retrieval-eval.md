# 검색(RAG) 후보 축소 측정

코드가 LLM 컨텍스트를 넘을 때 쓸 후보 축소 단계를 만들고, 정답 근거를 얼마나 남기는지 쟀다. 2026-10-26.
판정 파이프라인에는 아직 연결하지 않았다. 지금 매칭은 레포 전체 청크를 후보로 넣는다(full_context).

## 결론

- **화면 범위 안에서 로컬 임베딩(BGE-M3)으로 검색하면 상위 30개로 판정 근거의 약 90%(Spring)·94%(React)를 남긴다.**
  상위 50개면 96%·98%다. 화면 범위 평균(Spring 90개, React 56개)보다 후보가 줄어든다
- **키워드 검색(BM25)만으로는 부족하다.** 상위 30개로 66%·83%다. 기획서는 한국어, 코드는 영어 식별자라 단어가 덜 겹친다
- **BM25와 임베딩을 섞어도(RRF) 나아지지 않았다.** K ≥ 20에서 임베딩 단독보다 2~4%p 낮다. 섞는 방식(가중치)을 바꾸면 달라질 수 있다
- **화면 범위가 먼저다.** 같은 임베딩이라도 레포 전체에서 검색하면 상위 30개로 62%·74%로 떨어진다

## 방법

`python scripts/eval_retrieval.py` (LLM 호출 없음, 두 레포 약 1분. 임베딩은 `output/embeddings/`에 캐시)

- 질의: 요구사항 본문 + 분해한 조건 문장. 청크: 파일 경로·심볼 이름 + 코드 본문 (`matcher/retrieve.py`)
- BM25: 영문 식별자는 camelCase로 나누고, 숫자는 그대로, 한글은 2-gram (PDF 추출에서 띄어쓰기가 사라짐)
- 임베딩: `BAAI/bge-m3`, 로컬 실행 (코드가 외부로 나가지 않음). 최대 4096토큰이라 긴 컴포넌트 청크도 잘리지 않는다
- 정답 근거
  - 판정 근거: 최근 전체 판정(Spring 13, React 14)에서 판정 LLM이 고른 primary 근거
  - 매칭 근거: 매칭 LLM이 레포 전체에서 고른 근거(다른 화면 코드 포함)
- Recall@K = 요구사항별 (정답 ∩ 상위 K) / 정답의 평균. 근거가 없는 요구사항은 뺀다

## 결과 (판정 근거 Recall@K)

| K | 범위 BM25 | 범위 임베딩 | 범위 혼합 | 전체 임베딩 |
|---|---|---|---|---|
| Spring 10 | 53.2% | 61.1% | 59.9% | 38.2% |
| Spring 20 | 60.9% | 82.2% | 78.4% | 54.8% |
| Spring 30 | 65.6% | **89.7%** | 86.9% | 62.4% |
| Spring 50 | 77.5% | **95.6%** | 94.7% | 75.4% |
| React 10 | 61.3% | 66.0% | 67.5% | 46.9% |
| React 20 | 72.9% | 85.2% | 81.5% | 68.0% |
| React 30 | 83.3% | **94.1%** | 90.6% | 74.4% |
| React 50 | 92.3% | **98.2%** | 97.8% | 86.9% |

화면 범위 전체를 넣으면 판정 근거는 100%(판정이 이 화면 근거에서만 고르므로), 매칭 근거는 Spring 84.9%·React 89.6%다.
매칭 근거 중 빠지는 것은 대부분 다른 화면 코드로, 화면 범위가 일부러 빼는 것이다. 매칭 근거 기준 전체 표는 스크립트 출력에 있다.

## 한계

- **정답이 LLM이 고른 근거다.** 판정 근거는 전체 코드를 본 매칭 결과에서 출발했다. 사람이 고른 근거가 아니다
- **샘플이 작다.** 청크 304개·139개라 화면 범위 자체가 작다. 큰 코드에서 K를 얼마로 할지는 다시 재야 한다
- **검색 Recall은 판정 정확도가 아니다.** 실제로 판정에 연결해 골든셋 정확도(현재 82~84%)가 유지되는지가 최종 기준이다.
  이 단계는 판정 LLM을 다시 돌려야 해서 비용이 든다
- Contextual Retrieval(청크마다 LLM이 맥락 설명을 붙여 색인)은 비용 때문에 넣지 않았다. 지금은 파일 경로·심볼 이름만 붙인다

## 다음

1. 판정 파이프라인에 연결: 화면 범위 → 요구사항별 상위 K(30~50) → 기존 선택·판정. 골든셋으로 정확도 비교
2. 로컬 LLM 전환 때 기본값으로 검토. 컨텍스트가 짧은 모델에서는 화면 범위도 다 안 들어갈 수 있다
3. 혼합 가중치, 리랭커는 상위 K에 정답이 자주 빠질 때 다시 본다

설치: 임베딩은 선택 기능이다. `pip install sentence-transformers` (torch 포함, 모델 약 2.2GB는 첫 실행 때 받음).
없으면 `--no-dense`로 BM25만 잰다.

## 임베딩 모델 비교 (2026-11-13, #109)

`python scripts/compare_embeddings.py` (LLM 호출 없음). 같은 조건: 화면 범위 안 검색, 질의는 요구사항 본문 + 분해 조건,
정답은 판정 13·14가 고른 primary 근거. 색인 시간은 Apple M5(24GB) CPU/MPS 기준, 캐시 없이 처음부터.

| 모델 | Spring R@10 / 30 / 50 | React R@10 / 30 / 50 | 색인(초) S / R | 최대 입력 |
|---|---|---|---|---|
| BGE-M3 (기존) | 61.1 / **89.7** / 95.6 | 66.0 / 94.1 / 98.2 | 14.7 / 10.3 | 8192 (4096 사용) |
| KURE-v1 (BGE-M3 한국어 추가 학습) | 58.4 / 88.3 / 94.3 | 72.8 / 94.8 / 98.0 | 11.4 / 9.9 | 8192 (4096 사용) |
| multilingual-e5-large | 58.4 / 86.0 / 94.4 | 55.3 / 89.5 / 98.6 | 11.0 / 7.5 | **512** |
| **Qwen3-Embedding-0.6B** | **63.0** / 89.3 / **96.3** | **78.6 / 97.1 / 100.0** | **8.1 / 5.9** | 32768 (4096 사용) |

- **Qwen3-Embedding-0.6B를 기본값으로 정했다.** React에서 확실히 앞서고(R@30 97.1% vs 94.1%), Spring은 BGE-M3와 같은 수준이다
  (R@30 차이 0.4%p는 요구사항 100개 중 1개 미만의 차이). 파라미터가 가장 작아 색인도 가장 빠르다.
- e5는 512토큰에서 잘려 긴 컴포넌트·템플릿 청크를 다 보지 못한다. 한국어 특화(KURE)는 영어 코드가 섞인 이 작업에서 이점이 없었다.
- 한계: 정답이 LLM이 고른 근거이고 표본이 레포 2개·요구사항 약 100개다. 모델 간 1~2%p 차이는 우연일 수 있다.

## 매칭 입력·비용 추정 (2026-11-13)

`python scripts/measure_retrieval_cost.py --model qwen3-0.6b`. 매칭 후보 = 화면의 요구사항마다 상위 K개의 합집합.
토큰은 기존 full_context 실행(match_call.usage)의 캐시 토큰으로 글자당 토큰을 보정해 추정했다 (실제 호출 아님).

| | 화면당 후보 | 매칭 입력 토큰 (12화면) | 판정 근거 유지 | 추정 매칭 비용 |
|---|---|---|---|---|
| Spring 전체 코드 (현재) | 304 | 650,664 | 100% | $0.64 |
| Spring 검색 30 | 55 | 126,720 (-81%) | 96.9% | $0.63 |
| React 전체 코드 (현재) | 139 | 450,192 | 100% | $0.44 |
| React 검색 30 | 41 | 123,523 (-73%) | 100% | $0.62 |

- **입력 토큰은 70~80% 줄지만 현재 규모에서 비용은 줄지 않는다.** 전체 코드 방식은 모든 화면이 같은 목록을 보내 두 번째 화면부터
  캐시(0.1배 단가)로 읽는다. 검색 방식은 화면마다 후보가 달라 캐시를 쓰지 못한다.
- 매칭은 판정 1회 비용의 약 15%다. 비용 대부분은 판정 단계 출력 토큰이다 (Spring 판정 $2.91 중 출력 $1.80).
- 이 단계의 이점은 비용보다 규모다. 전체 코드 방식의 입력은 레포 크기에 비례해 커지고(Spring 4천 줄에서 화면당 5.4만 토큰),
  검색 방식은 요구사항 수 × K에 묶인다. 문맥이 짧은 모델이나 큰 레포에서 차이가 난다.
- 판정 정확도가 유지되는지는 아직 재지 않았다 (`python scripts/run_match.py retrieval <repo>` 후 판정·골든셋 채점, API 비용 발생).

## 화면별 후보의 캐시 쓰기 할증 제거 (2026-11-16)

Anthropic 클라이언트는 `context`로 받은 블록에 항상 `cache_control`을 건다. 전체 투입(full_context)은 모든 화면이
같은 목록이라 두 번째 화면부터 0.1배로 읽지만, 화면마다 후보가 다른 screen_scope·retrieval은 같은 목록을 다시 읽지
않으므로 쓰기 할증(1.25배)만 낸다. 그래서 화면별 후보는 캐시 블록이 아니라 사용자 프롬프트로 보내도록 바꿨다
(`select_for_screen(cache_candidates=False)`, `run_match.py`는 full_context가 아니면 자동 적용).
웹 검증 실행기는 모든 화면에 같은 전체 목록을 보내므로 그대로 캐시한다.

기존 실행 기록으로 다시 계산한 값 (새 호출 없음):

| | 비용 |
|---|---|
| 검색 매칭 화면 2개 (match run 6, 실측) | $0.172 |
| 같은 호출을 캐시 쓰기 없이 보냈다면 | **$0.146 (-15%)** |

레포 크기별 매칭 비용 추정 (화면 12개, 전체 투입은 첫 화면 쓰기 1.25배 + 나머지 읽기 0.1배, 검색은 일반 입력 1배):

| 코드 크기 | Spring 전체 투입 / 검색 | React 전체 투입 / 검색 |
|---|---|---|
| 지금 (x1) | $0.64 / $0.63 | $0.44 / $0.62 |
| x2 | $1.27 / $0.63 | $0.88 / $0.62 |
| x5 | $3.19 / $0.63 | $2.20 / $0.62 |
| x10 | $6.37 / $0.63 | $4.41 / $0.62 |

- **Spring 크기(약 4천 줄)가 손익분기점이다.** 그보다 크면 검색이 싸고, 코드가 커질수록 차이가 벌어진다.
- 검색 쪽 비용을 고정으로 본 것은 가정이다. 후보는 요구사항 수 × K(30)의 합집합이라 레포가 커져도 상한이 있지만,
  화면 범위가 커지면 조금 늘 수 있다. 큰 레포에서 실측하지 않았다.
- 판정 단계는 바꾸지 않았다. 같은 화면의 요구사항들이 같은 근거 묶음을 반복해 읽어 캐시가 이득이다(판정 run 15에서 캐시 읽기 167,098토큰).

## 웹 코드 검증 연결 (2026-11-16)

웹 검증(`api/v2/verification_runner.py`)은 화면마다 후보를 줄여 매칭한다. 11/20부터 기본값이며, `SPECPILOT_MATCH_STRATEGY=all_chunks`로 전체 투입을 쓸 수 있다.
기본값은 지금과 같은 전체 투입이다.

- 후보 = 요구사항마다 화면 범위 안 상위 30개 + 화면 밖 상위 5개의 합집합. 화면 밖 후보를 조금 남겨 두는 이유는
  "이 화면엔 없고 다른 화면 코드만 있음"(rule_other_screen_only) 판정이 매칭이 다른 화면 코드를 고를 수 있어야 동작하기 때문이다.
- 후보는 캐시 블록이 아니라 프롬프트로 보낸다(쓰기 할증 방지). 응답 재사용(docs/response-cache.md)과 합쳐져,
  코드를 고쳐도 후보 목록이 그대로인 화면은 매칭을 다시 부르지 않는다.
- 임베딩 모델은 `SPECPILOT_EMBEDDING_MODEL`(기본 qwen3-0.6b). sentence-transformers나 모델이 없으면 전체 투입으로 돌아가고
  `analysis_metrics.retrieval_fallback`에 이유를 남긴다. 색인 시간은 `retrieval_duration_ms`.
- 웹에서 실제 모델로 정확도·비용을 재지는 않았다. 같은 방식의 파이프라인 측정은 위 "판정 정확도 확인" 절을 본다.

웹은 DB 사본에서 `SPECPILOT_MATCH_STRATEGY=retrieval`로 같은 24개 요구사항을 검증했다.

**매칭만 effort low: 채택하지 않는다.**
- 매칭 출력은 원래 작다(화면 2개 1,085 → 1,004토큰). 사고량을 낮춰도 줄일 출력이 없다.
- 비용 차이는 같은 조건(캐시 쓰기 없음) 추정 $0.146 대비 $0.143로 2% 남짓이다. 반면 결함 통과가 2 → 3으로 하나 늘었다.
- 비용의 대부분은 판정 단계 출력이므로, 사고량을 조절한다면 판정 쪽에서 해야 한다(docs/effort-eval.md).

**임베딩 직결(매칭 LLM 생략): 기본값으로 쓰지 않는다. 대신 비용 절감 옵션으로 남긴다.**
- 매칭 비용이 0이 되어 화면 2개 기준 실행 비용이 약 18% 준다($0.83 → $0.68).
- 판정 비용은 늘지 않았다. 규칙 사전 판정(근거 없음 → not_found)이 막힐 걱정이 있었지만, 규칙으로 정해진 조건 수가 7개로 같았다.
  판정 LLM이 넘겨받은 근거가 관련 없다고 보면 스스로 not_found를 냈다.
- 결함은 더 많이 잡았다(14~15 → 17). 하지만 정상을 결함으로 본 오탐이 0~2 → 3으로 늘고 일치율이 72%로 가장 낮다.
  관련 없는 코드가 섞여 판정이 보수적으로 기운 것으로 보인다. 신뢰를 우선하는 설계 원칙상 기본값은 매칭 LLM을 유지한다.

**웹 실행기 검색 모드: 동작과 비용을 확인했다.**
- 화면 2개에 $0.86, 4분 20초(매칭 13초, 판정 3분 49초, 임베딩 색인 14초). 파이프라인 검색 방식($0.83)과 같은 수준이다.
- 정확도도 같은 수준이다(79%). 결함 통과는 1개로 이번 실험 중 가장 적었다. 같은 정책을 다시 돌려도 판정의 약 14%가
  바뀌므로 다른 방식과의 차이는 흔들림 범위 안이다.
- 새로 추가한 `analysis_metrics.estimated_cost_usd`가 실제 실행에서 단계별로 기록되는 것을 확인했다.
- 코드와 요구사항을 그대로 두고 같은 검증을 다시 돌리면 매칭 2회·판정 23회가 모두 응답 재사용(docs/response-cache.md)으로 처리되어
  **17초, $0**였다(처음 4분 20초, $0.86). 검색 후보가 결정적이라 재사용 키가 그대로 맞는다.

한계: 화면 2개, 방식마다 1회 실행이다. 전체 화면과 반복 실행으로 확인하지 않았다.

## Java 동명 메서드 구분 (11/19, #50)

`memberService.signup()` 같은 호출에서 수신 객체의 선언 타입을 읽어 그 클래스와 구현 클래스의 메서드만 잇는다. 타입은 호출하는 메서드 본문의 지역 변수·매개변수 선언과 같은 클래스의 필드 선언에서만 찾고, 찾지 못하면 예전처럼 동명 메서드 전부로 잇는다.

Spring 화면 범위(청크 수) 변화는 다음과 같다. React는 변화 없다.

| 화면 | 전 | 후 |
|---|---|---|
| LOGIN-002 | 78 | 72 |
| LOGIN-004 | 74 | 68 |
| NOTICE-004, 005 | 146 | 76 |
| MYPAGE-001, 002 | 116 | 85 |

공지 상세·수정 화면이 회원·비밀번호 코드를, 마이페이지가 공지 코드를 더 이상 끌어오지 않는다. 지난 Spring 판정 실행들이 근거로 인용한 청크 596건 중 범위에서 빠진 것은 0건이라 근거 손실은 없다.

## 단계별 모델 지정과 비교 (11/20, API 사용)

`SPECPILOT_LLM_MODEL_<단계>`로 단계마다 모델을 따로 고를 수 있다. 단계는 `EXTRACTION`, `MATCHING`, `JUDGMENT`, `GENERATION`이고, 지정하지 않은 단계는 `SPECPILOT_LLM_MODEL`을 쓴다. 매칭과 판정이 다른 모델이면 클라이언트를 따로 만들고, 단계별 비용도 그 단계 모델 단가로 계산한다.

같은 조건(웹, DB 사본, Spring 2개 화면 24개 요구사항, 검색 후보, 응답 재사용 끔)에서 한 번씩 돌렸다. 정답은 골든셋 47개 판정 조건이다.

| 매칭 / 판정 | 일치 | 결함 잡음 | 결함 통과 | 오탐 | 확인 필요 | 비용 | 시간 |
|---|---|---|---|---|---|---|---|
| Opus 5 / Opus 5 (11/18 기준선) | 37 (79%) | 15 | 1 | 2 | | $0.86 | 4분 20초 |
| Opus 5.5 / Opus 5.5 | 35 (74%) | 13 | 0 | 1 | 6 | $0.69 | 3분 31초 |
| **Haiku 5.5 / Opus 5** | **37 (79%)** | 15 | 1 | **0** | 3 | $0.63 | 4분 29초 |
| Sonnet 5.5 / Sonnet 5.5 | 22 (47%) | 11 | 0 | 1 | 21 | $0.19 | 1분 12초 |
| **Haiku 5.5 / Sonnet 5.5** | **37 (79%)** | **17** | 1 | 4 | 1 | **$0.19** | 2분 9초 |

해석
1) 매칭을 Haiku 5.5로 바꾸면 매칭 비용이 $0.19에서 $0.006으로 줄고 정확도는 그대로다. 매칭은 후보 중 고르기라 작은 모델로 충분하다. 판정이 Opus면 오탐도 0건이었다.
2) Sonnet 5.5로 매칭까지 하면 고르는 청크가 적어 확인 필요가 21건으로 늘었다. 매칭에는 맞지 않는다.
3) Haiku 매칭 + Sonnet 판정은 기준선의 22% 비용으로 같은 일치율을 냈고 결함을 가장 많이 잡았지만 오탐이 4건이다. 비용이 중요한 반복 검증에 쓸 만하다.
4) 한 번씩 돌린 결과라 1~2건 차이는 흔들림 범위일 수 있다.

권장 설정: 정확도 우선이면 `SPECPILOT_LLM_MODEL_MATCHING=claude-haiku-5-5`(판정은 기본 Opus), 비용 우선이면 여기에 `SPECPILOT_LLM_MODEL_JUDGMENT=claude-sonnet-5-5`를 더한다. 기본값은 바꾸지 않았다.
