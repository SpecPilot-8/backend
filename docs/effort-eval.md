# 판정 사고량(effort)과 출력 토큰

판정 단계 비용의 대부분은 출력 토큰이고, 그 대부분은 모델이 답하기 전에 하는 사고(adaptive thinking)다.
화면에 저장되는 JSON(상태·근거 id·한두 문장 사유)은 짧다. 사고량은 `SPECPILOT_LLM_EFFORT`(기본 high)로 바꾼다.
사고량이 기본이 아니면 판정 재사용 키(`input_hash`)에 들어가, 다른 사고량의 판정을 재사용하지 않는다.

## 측정 (2026-11-13, API 사용)

Spring NOTICE-002·LOGIN-001(조건 54개, 판정 시도 47개), 같은 매칭 결과(match run 6, 검색 30)에 사고량만 바꿔 판정했다.

| | high (run 15) | medium (run 16) | low (run 17) |
|---|---|---|---|
| 출력 토큰 | 17,764 | 12,020 (**-32%**) | 7,582 (**-57%**) |
| 판정 비용 (입력 포함) | $0.67 | $0.52 (-22%) | $0.41 (**-39%**) |
| 골든셋 일치 | 37/47 (79%) | 39/47 (83%) | 37/47 (79%) |
| 결함 19개 중 잡음 | 14 | 15 | 14 |
| **결함을 implemented로 통과** | **2** | **4** | **3** |
| 정상 28개 중 오탐 | 0 | 0 | 0 |

입력 비용(약 $0.26)은 사고량과 무관해서 출력 감소폭보다 비용 감소폭이 작다.

## 해석

- **출력 토큰과 비용은 확실히 준다.** low에서 출력 57%, 판정 비용 39% 감소.
- **일치율은 비슷하지만, 결함을 implemented로 통과시키는 경우가 2 → 3~4개로 늘었다.** 이 도구에서 가장 비싼 오류다
  (틀린 '구현됨'은 사람이 다시 보지 않는다). 늘어난 것은 NOTICE-002-2·3(게시일/종료일 순서 에러 문구), NOTICE-002-7(첨부 50MB)로,
  high는 partial로 결함을 잡았던 조건들이다. 사고를 줄이면 "코드가 비슷하게 있다 → 구현됨"으로 빨리 결론 내는 경향으로 보인다.
- 화면 2개·1회 실행이라 차이 1~2개는 흔들림일 수 있다. **기본값은 high로 둔다.** 사고량을 낮추려면 전체 화면을
  여러 번 돌려 '결함 통과' 수가 늘지 않는지 먼저 확인해야 한다.
- 비용을 줄이면서 위험을 덜 키우는 대안: 결함 신호가 있는 조건(규칙 단계에서 근거가 약하거나 문구 비교가 있는 조건)만 high,
  나머지는 low로 나누기. 아직 구현하지 않았다.
