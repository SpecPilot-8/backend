# 시험 설계 근거와 관점 점검

갱신일: 2026-10-30 · 계획 `design-plan-v1` · 생성 프롬프트 `testgen-v2-design`

## 사용자가 확인할 내용

시험을 읽으며 다음 세 질문에 답할 수 있어야 한다.

1. 어떤 요구사항의 어떤 수락 조건을 시험하는가? 생성에 사용한 요구사항 개정, 원문 인용, PDF 페이지를 확인한다.
2. 왜 이 절차와 입력값을 선택했는가? 시험 전체 목적과 단계별 절차·입력값/역할 선정 이유를 구분한다.
3. 빠진 시험은 없는가? 조건별 권장 관점과 실제 저장된 시험 단계의 연결을 비교한다.

기대 결과의 기준은 **검증 실행에 고정된 승인 명세·조건·검토 메모**다. 코드 판정은 별도 예측에만 사용한다. 현재 코드의 결함을 정상 기대 결과로 바꾸지 않는다. 모델이 작성한 설명은 사용자가 원문과 대조할 수 있는 짧은 설계 설명이며, 숨겨진 추론 과정이나 정확성 증명이 아니다.

## 생성 흐름

`승인 조건 → 규칙으로 권장 관점 제안 → 사용자 계획 확인 → 관점별 시험·이유 생성 → 조건/관점 연결 점검`

- 준비 요청은 모델을 호출하지 않는다. 조건 분류와 명시된 표현으로 관점을 제안한다.
- 입력 검사는 허용/거부, 이동은 시작 상태와 동작 후 상태, 데이터는 처리 결과, 표시는 요소/형식, 오류는 실패 상황/안내를 확인한다.
- 수치 제한이 명시된 경우 경계값을 추가한다. 권한·상태·데이터 없음도 해당 표현이 있을 때만 제안한다. 정적 검증 불가 조건은 실행 화면 확인을 제안한다.
- 이 계획은 보수적인 규칙 제안이다. 업무 위험, 조합, 동시성, 성능, 보안, 접근성 등 필요한 모든 시험을 자동 판단하지 않는다. 명세에 없는 정책을 새로 만들지 않으며 별도 요구사항 보완과 수동 시험이 가능하다.
- 웹 생성은 소주제별 기존 모델 호출에 계획과 설명 필드를 함께 전달한다. 추가 모델 호출 단계는 없지만 입출력 토큰과 비용은 늘 수 있다.

## API

### 준비

`POST /api/v2/projects/{p}/test-specifications/generate/prepare`

기존 응답에 `design_plan`을 추가한다. 항목에는 `id`, 요구사항 ID/개정/제목, 조건 ID/키/본문, `perspective`, 한글 `label`, 선정 기준 `reason`이 있다. `origin=rule_suggestion`이며 한계도 반환한다. 계획의 ID는 사용자가 보게 될 시험의 원문 조건과 연결된다.

실행 요청은 기존 필드와 `design_plan_version`을 전달한다. 준비 화면과 서버의 계획 버전이 다르면 모델 호출 전 `409 CONFIG_CHANGED`로 거부한다. 조건과 모델 설정은 기존 검증 실행·설정 버전 검사로 고정한다.

### 생성 결과 저장

```json
{
  "design": {"rationale": "제목 상한에서 허용과 거부를 비교한다.", "generated_revision": 1, "origin": "model"},
  "steps": [{
    "step_key": "s1",
    "design": {
      "intent_ids": ["NOTICE-C1::boundary"],
      "rationale": "최대 허용 길이와 같은 값을 입력해 경계 처리를 확인한다.",
      "input_rationale": "명세의 상한 50자를 선택했다. 다른 필수 입력은 유효하게 준비한다.",
      "basis": "specification"
    }
  }]
}
```

위는 추가 필드만 보여주는 예시다. 기존 action/expected/test_data/requirement_links 등은 그대로 필수다. `basis=review_needed`는 명세 밖의 해석·가정 확인이 필요한 단계다. 원문 없는 오류 문구·권한명·환경은 확정하지 않는다.

모델의 `uncovered_intents`는 내부 어댑터의 `design_gaps:[{intent_id,reason}]`로 변환한다. 같은 관점을 작성과 누락에 동시에 제출하거나, 다른 조건의 관점/임의 ID/공백 이유를 제출하면 거부한다. 서버는 ID·개정·참조를 검사하며 설명의 의미적 정확성까지 증명하지 않는다.

### 점검 조회

`GET /api/v2/projects/{p}/test-specifications/{t}/design-review?revision=2`

- 사양서의 지정 개정과 그때 고정한 시험 개정으로 집계한다. `test_specification_id`, `specification_revision`, `plan_available`, `items`, `conditions`, `summary`, `limitations`를 반환한다.
- `written`: 원래 생성 절차의 명세 기반 단계에 관점이 연결됨. 화면은 **시험 연결됨**으로 표시한다.
- `review_needed`: 명세 밖의 해석이 있거나 생성 후 절차를 수정하여 설명 재검토 필요.
- `missing`: 해당 관점에 연결된 설계 기록 없음. 제공된 미포함 이유가 있으면 같이 표시한다.
- 조건 연결과 관점 연결은 구분한다. 수동 시험이 조건에 연결돼도 모델의 관점을 임의로 배정하지 않는다.
- 위 상태는 시험의 충분성·의미적 적합성·실제 수행 통과율이 아니다.

## 편집·과거 자료

설계 설명은 생성 당시 기록이다. 사용자가 제목·사전 조건·절차·입력값·기대 결과를 수정하면 시험 개정을 증가시키고 원래 `generated_revision`은 보존하여 재검토로 표시한다. 기존 설명을 편집 요청으로 위조할 수 없다. 새 단계나 다른 조건으로 연결을 바꾼 단계에는 기존 설명을 자동 상속하지 않는다. 수행 결과만 변경하면 절차 설명을 무효화하지 않는다.

과거 사양서와 수동 자료는 설명·관점 계획이 없을 수 있다. `plan_available=false`와 미기록 안내를 표시하고 실제 저장된 조건 연결만 확인한다. 새 이유를 추정해서 채우지 않는다. 새 AI 사양서를 생성할 때부터 추가 기록을 남긴다.

## Excel과 검증

기본 10열 시험표와 실제 O/X 의미는 유지한다. `include_analysis_detail=true`일 때 분석 상세에 시험/절차/입력값 선정 이유와 설명 상태를 추가한다. 계획이 있으면 **시험 설계 점검**, 없으면 **원문 연결 점검** 시트를 추가한다. 지정 사양서 개정과 실제 수행 회차를 고정하며 출력 행 한도를 적용한다.

검증은 가짜 모델 응답을 이용한 API·저장·참조·편집·개정·Excel 통합 테스트와 분리 DB의 화면 점검으로 수행한다. 실제 모델의 설명 품질과 업무별 시험 충분성은 실제 기획서로 별도 평가해야 한다.
