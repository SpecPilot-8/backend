# 기획서 파싱 담당 개발·인계 체크리스트

갱신일: 2026-10-10 · 연결 기준: 기능명세 2.4 / DocumentArtifact 2.1 / 요구사항 추출 2.2 / 시험 생성 2.1

**팀원 1에게 이 문서를 먼저 전달한다.** 필드 정의는 [파싱 출력 계약](PARSER_OUTPUT_SPEC.md), 서비스 기능은 [기능명세](FUNCTIONAL_SPEC.md), 코드 분석·시험 생성 담당은 [모델 담당 명세](MODEL_TEAM_GUIDE.md), Excel 매핑은 [테스트 출력 계약](TEST_OUTPUT_SPEC.md)을 따른다.

제공된 `한성대 specpilot 기획서 ver0.2.pdf`는 우리 서비스의 **분석 입력 예시**, `SpecPilot 테스트 케이스 및 결과.xlsx`는 **내보내기 형식 예시**다. 아래 로그인·공지사항·마이페이지는 입력 문서의 기능이며 파싱 모듈이 분석해야 할 데이터다. 문서가 바뀌면 기능명·수치·화면 수·요구사항 수도 달라져야 한다.

## 1. 팀원 1의 개발 목표

원본 기획서 전체를 읽고 **주제 → 소주제 → 요구사항 → 원자 수락조건**으로 구조화한다. 모든 규칙·분기·오류 메시지를 원문 페이지·블록·표시 번호로 추적할 수 있어야 한다. 일부 대표 항목만 반환하는 요약기가 아니라 요구사항을 빠짐없이 구조화하는 모듈을 개발한다.

출력은 다음 두 단계다.

1. **DocumentArtifact 2.1**: 문서 ID·revision·해시, 모든 페이지의 블록·원문·위치·읽기 순서·Description/Action 번호·읽기 실패와 경고.
2. **RequirementExtractionDraft 2.2**: 주제·소주제·화면/상태·요구사항·수락조건·수치 규칙·출처·모호성. [JSON Schema](schemas/requirement-extraction.schema.json)를 만족하는 객체 한 개.

[현재 문서 블록 예시](examples/document-artifact.json)와 [추출 예시](examples/requirement-extraction.json)는 사람이 확인한 일부 발췌다. 예시에 있는 4개 요구사항을 완료 범위나 고정 항목으로 사용하지 않는다. 전체 출력은 아래 화면별 범위를 포함해야 한다. 별도 코드나 실제 시험 결과 없이도 문서 추출은 실행할 수 있어야 한다.

원문 ‘통합 로그인’·‘공지사항 관리’ 등의 Depth는 screens[].depth_path에 보존한다. 위 ‘인증’ 등 묶음은 표시를 위한 분류 제안이며, 원문과 다른 그룹명을 제안하면 title_origin=inferred와 검토 사유를 사용한다. 화면 제목을 정리해도 source_title에는 원문을 남긴다.

2·4·6쪽처럼 설명 번호가 없는 오류 예시는 annotation 블록으로 남기고 기본 화면의 관련 조건에 출처를 추가한다. 같은 문구가 반복돼도 페이지 근거를 없애지 않는다. 이미 추출한 규칙의 오류 상태인지 새 규칙인지 구분한다.

화면 예시 계정·이름·게시물 4건·샘플 날짜는 실제 업무 규칙과 분리해 원문 블록에 보존한다. 페이지/상태 확인 없이 문서에 없는 관리자 권한·성공 후 이동·경계 단위 정의를 추가하지 않는다.

| 오류 발생 조건·문구·발생 시점 | requirement.condition/action, error_message 조건 text/source_refs | **F03** 오류 조건 검토, **F05** 처리/문구 비교, **F07** 오류 시험의 단계 expected | 팀원 2가 코드 근거·문구 일치 정보 추가 |

F01의 프로젝트·모델 설정은 서버/사용자가 제공한다. 팀원 1이 API 키·모델 카탈로그를 문서에서 생성할 필요는 없다. F06의 코드 근거·파일·줄·호출 흐름은 팀원 2/코드 파서가 만든다. F08의 실제 결과·통과/실패·수행 일시는 사람이 시험한 뒤 별도 API에 기록한다.

## 4. 연결 예: 제목 50자 제한

원문: PDF 9쪽 Description 1. 기존 [추출 JSON](examples/requirement-extraction.json)의 NOTICE-002-1을 참고한다.

1. **F02 / 팀원 1**: `공지사항 → 공지사항 작성`, NOTICE-002, Description 1, 제목 규칙 원문·출처를 추출한다.
2. **F03 / 사용자**: ① 50자까지 허용 ② 50자 초과 입력 차단 ③ 오른쪽 아래 글자 수 표시를 각각 검토한다. 문자 수 계산 방식이 미정이면 확인 사유를 남긴다.
3. **F05·F06 / 팀원 2**: 검토 확정한 각 조건 ID·revision으로 코드의 제한값/차단/표시 처리를 판정하고 실제 파일·줄·근거를 연결한다. 팀원 1은 코드가 구현됐는지 출력하지 않는다.
4. **F07 / 팀원 2**: 확인된 문자 수 정의로 50자 허용·51자 초과 입력 차단·입력 길이 표시 시험을 생성한다. 각 단계는 requirement_links로 해당 조건에 연결한다. 생성한 시험 문자열은 업무 규칙이 아닌 시험 데이터다.
5. **F08 / 사용자**: 실제 수행 후 단계별 결과를 편집하고 저장한다. AI 예측을 O/X로 기록하지 않는다.
6. **F09 / 백엔드**: 시험번호·DEPTH(1)/(2)·단계 번호·절차·expected·계정·입력값·비고·실제 확인결과를 제공된 Excel 형식으로 내보낸다.

공통 추적 경로는 **원문 block_id → 요구사항 stable_key → 조건 stable_key → 서버 ID/revision → 판정 근거 → 시험 단계 requirement_links → 실제 회차/단계 결과 → Excel 행**이다. 팀원 1은 앞의 원문·후보 키·조건까지 제공하고 저장/검토 확정 이후의 ID는 서버가 발급한다.

| 전체 입력 블록 | 이 PDF의 15쪽 전체 원문·화면 메타데이터·설명/동작/annotation 블록 | 읽지 못한 페이지/영역은 명시, 성공처럼 숨기지 않음 |
| 전체 추출 JSON | 위 화면별 모든 규칙·분기·오류·수락조건, 출처·검토 사유 | Schema 통과 및 키/출처/숫자/단위/연산자 유효성 검사. 4개 발췌 예시로 대체하지 않음 |
| 원문 범위 대조표 | 페이지 + Description/Action/annotation 항목별로 반환한 requirement/condition 후보 키 연결. 규칙 아님/중복/미해석/미읽기는 이유 기록 | 모든 원문 항목의 처리 결과를 확인할 수 있음. 제목·장식 이미지는 규칙 아님으로 설명; 중복은 기존 결과/추가 출처 연결 |
| 평가·실패 자료 | 사람이 검토한 정답, 추출 누락/과잉 생성/원문 인용/숫자 보존 평가, 미지원·빈 결과·모순·OCR 실패 사례 | 미측정 지표를 달성으로 보고하지 않음. 문서의 모순을 임의 수정하지 않음 |

원문 범위 대조표는 이 예시를 인수하기 위한 별도 검토 자료다. 현재 RequirementExtractionDraft 2.2에 정의되지 않은 coverage 필드를 임의 추가하지 않는다. 서비스의 실시간 누락 경고는 기존 warnings/unread_locations/review_reasons를 사용하고, 대조표의 API 연동은 필요 시 별도 계약으로 정한다.

요구사항 개수는 고정하지 않는다. 원문 표시 번호 한 개에 여러 규칙이 있으면 여러 조건으로 분해하고, 같은 규칙이 다른 화면에 나타나면 적용 화면과 출처를 모두 보존한다. 색상·배치·높이처럼 실제 렌더링 확인이 필요한 항목도 추출하되 not_statically_verifiable로 구분하고 코드로 확인 가능한 동작은 별도 조건으로 남긴다.
