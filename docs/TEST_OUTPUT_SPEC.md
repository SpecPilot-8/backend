# 단계별 테스트 JSON 및 Excel 출력 계약

문서 버전: 2.4 · 시험 생성 계약: 2.1 · 보고서 매핑 계약: 1.0 · 갱신일: 2026-10-10

팀원 2와 백엔드 출력 담당이 함께 사용하는 **개발 목표 계약**이다. 제공받은 `SpecPilot 테스트 케이스 및 결과.xlsx`의 형식에 맞춘다. 이 문서 변경으로 실제 생성기·Excel 출력기가 구현되는 것은 아니다. [모델 담당 안내](MODEL_TEAM_GUIDE.md), [API 명세](API_SPEC.md)와 함께 읽는다.

## 1. 원본에서 확인한 구조

- 시트: 개정이력, 00. 목차, 01. 로그인, 02. 회원가입, 03. 비밀번호찾기, 04. 공지사항, 05. 마이페이지, 06. 권한.
- 시험 시트 A1:J2: 프로젝트명·시험대상 메뉴명·사양서작성자·사양서작성일·테스트확인자·테스트시행일.
- 4·5행: 두 줄 헤더. 6행은 안내 예시이며 시험 건수가 아니다. 실제 데이터는 7행부터다.
- A열의 동일 시험번호가 여러 행에 반복된다. `04. 공지사항!A20:A22`의 NOTICE-CREATE-001은 단계 1·2·3을 갖는 시나리오 하나다.
- 확인결과는 실제 데이터 행에서 비어 있다. 6행의 `정상:O/비정상:X`는 표시 방식 안내이며 수행 결과가 아니다.

**시험번호 하나 → 단계 여러 개 → 단계별 예상결과·시험데이터·확인결과** 구조를 사용한다. 서로 다른 기대 결과를 마지막 단계의 값 하나로 덮어쓰지 않는다. 기존 문자열 steps[]는 필드별 정보가 부족하므로 단계 객체 배열로 바꾼다.

## 2. 생성 모델 출력

[모델 출력 JSON 예시](examples/test-generation.json), [JSON Schema](schemas/test-generation.schema.json)를 전달한다.

| 필드 | 의미 |
|---|---|
| contract_version | `2.1` |
| verification_run_id | 검증 실행을 고정 |
| test_candidates[].candidate_key | 출력 내 고유 후보 키. 최종 시험번호·DB ID는 서버가 발급 |
| export_section_key / subtopic_id | 출력 시트 영역과 검토된 기능 소속. 서버가 제공한 후보에서 선택 |
| title / type / preconditions | 시나리오 이름·positive/negative/boundary·시작 전 준비 조건 |
| requirement_links[] | `{requirement_id,requirement_revision,condition_ids[]}`. 모든 단계 참조의 중복 없는 합집합 |
| steps[] | 단계별 step_key·order·action·expected·test_data·requirement_links |
| steps[].test_data | `{account,input,notes}`. Excel 계정·입력값·비고에 각각 연결 |
| prediction | 코드 예상 결과. 명세 expected 및 실제 확인결과와 별도 |
| assumptions / warnings | 준비 필요·자료 충돌·미확정 조건 |

계정은 사용 역할이나 서버가 제공한 시험 계정 참조다. 모델이 비밀번호·실제 자격정보를 만들지 않는다. 계정이 적용되지 않으면 null, 입력·비고가 없으면 빈 문자열을 반환한다. 시험 데이터는 원문 규칙이 아니므로 생성한 값과 원문 수치를 구분한다.

25MB 파일 예시는 PDF의 50MB 이하 규칙 안에서 만든 시험 입력이다. PDF에 300MB 제한은 없다. MB 바이트 정의가 모호하므로 정확한 50MB 경계 입력은 단위 확인 후 생성한다. 모델 출력에는 실제 status·actual·performed_at·O/X를 허용하지 않는다.

## 3. 단계와 실제 수행 결과

서버는 TestCase(시나리오) ID와 표시용 test_no를 부여하고 단계별 step_key를 검증·보존한다. step_key는 시나리오 안에서 고유하며 순서(order)와 별개다. 순서를 바꿔도 기존 단계의 결과를 다른 행으로 옮기지 않는다. 신규 단계는 새 키를 사용한다. order는 1부터 연속이며 단계 수는 1..100이다.

실제 수행 한 회차는 `{test_case_id,test_case_revision,attempt_no,version,step_results[]}`다. step_results의 각 항목은 `{step_key,status,actual,notes,performed_at}`다. 회차·단계 키가 해당 절차 revision에 속하는지 검사한다. 기록 없는 단계는 조회에서 not_run으로 표시하며 실제 결과를 생성하지 않는다.

통과·실패는 actual과 performed_at이 필수이고 보류는 notes에 사유가 필요하다. 실제 기록은 사람이 편집 모드에서 입력한 뒤 저장 버튼으로 확정한다. 행 선택·입력·포커스 이탈·AI 예측은 저장을 실행하지 않는다. 절차 수정 뒤 과거 회차를 새 단계에 재연결하지 않는다.

시나리오 요약 상태는 서버가 계산한다: 단계에 failed가 있으면 failed, 그 외 on_hold가 있으면 on_hold, 모든 단계가 passed이면 passed, 그 외는 not_run이다. 일부만 통과하고 나머지 미실행이면 전체 통과로 표시하지 않는다. 단계별 집계와 시나리오별 집계를 이름·분모로 구분한다.

## 4. JSON → 원본 Excel 열 매핑

| 열 | 원본 헤더 | JSON 기준 |
|---|---|---|
| A | 시험번호 / 시나리오명 | TestCase.test_no. 동일 시나리오의 모든 행에 반복. 별도의 DB ID는 내부 보존 |
| B | 시험구분 DEPTH(1) | Topic의 템플릿 표시 이름. 예: 인증, 공지사항 |
| C | 시험구분 DEPTH(2) | Subtopic의 템플릿 표시 이름. 예: 로그인, 신규등록 |
| D | No | 단계 order. 각 시나리오에서 1부터 |
| E | 시험절차 | 단계 action |
| F | 예상결과 | 단계 expected. 코드 prediction을 넣지 않음 |
| G | 시험데이터 / 계정 | 단계 test_data.account. null은 `-` 표시 |
| H | 시험데이터 / 입력값 | 단계 test_data.input |
| I | 시험데이터 / 비고 | 단계 test_data.notes. 실제 수행 notes와 구분 |
| J | 확인결과 | 선택 회차의 해당 step_key 결과. passed는 O, failed는 X, on_hold는 보류, not_run 또는 회차 없음은 빈 셀 |

UI에서는 `공지사항 → 공지사항 작성`, 템플릿에서는 `공지사항 → 신규등록`처럼 표시할 수 있다. 서버의 export profile에서 동일 subtopic_id의 표기 별칭을 매핑하고 제목만으로 서로 다른 기능을 합치지 않는다. 목차의 DEPTH(3)/(4) 헤더는 원본에 존재하지만 이 예시에서 값이 비어 있어 임의의 하위 계층을 추가하지 않는다.

[보고서 매핑 JSON 예시](examples/test-report.json)는 원본 공지사항 20~22행 형식을 보여준다. 조회/출력 서비스가 조합하는 형식이며 LLM 반환 계약이 아니다. 시험계정 이메일은 공유용 `${qa_admin_email}` 참조로 대체했다. 확인결과의 null은 실제 Excel 빈 셀로 출력한다. 예시의 예상결과가 모두 PDF에서 검토 확정된 것은 아니므로 경고와 함께 제공한다.

metadata와 revision_history는 프로젝트·작성자 입력·저장 이력에서 가져온다. 사양서작성일과 테스트시행일은 다르며 수행하지 않았다면 테스트시행일은 비워둔다. 작성자·확인자·미지정 날짜를 모델이 채우지 않는다. 00. 목차는 선택 출력 시트·그룹에 맞게 생성하고 목차번호·메뉴 코드 규칙은 export profile로 고정한다. 원본의 빈 서식 1000행을 시험 데이터 1000건으로 세지 않는다.

템플릿 기본 10열·두 줄 헤더·프로젝트 메타데이터·개정이력·목차·기능별 시험 시트 구성을 유지한다. 코드 예측·원문·근거·실제 결과 상세·메모·회차는 API/화면과 별도 분석 상세 시트에 담아 연결할 수 있지만 원본 F/J열의 의미를 바꾸지 않는다.

## 5. 원본의 불일치와 검토 정책

| 근거 | 확인 내용 | 처리 |
|---|---|---|
| PDF 5쪽 Description 0·2 | 화면/항목 0은 이메일·이름, 항목 2는 비밀번호라고 설명 | SOURCE_CONTRADICTION. 입력 항목을 임의 확정하지 않음 |
| PDF 9쪽 Action D | 저장 설명이 `제목, 게시 시작일, 게시 종료일, 게시 내용을 확`에서 잘림 | SOURCE_TRUNCATED. 저장 후 이동 목적지를 추정하지 않음 |
| PDF 11쪽 Action D / Excel 04. 공지사항 F27 | PDF 수정 저장 후 목록 이동, Excel은 상세 화면 반영 | EXPECTATION_CONFLICT. 최신 승인 명세를 기준으로 검토 후 시험 expected 결정 |
| Excel 02. 회원가입 7·8행 | SIGNUP-001의 단계 1이 중복됨 | DUPLICATE_STEP_NUMBER. 원본 위치를 보존하고 검토; 임의 삭제·번호 변경 금지 |
| PDF 8쪽 그림 / Excel 04. 공지사항 F9 | 그림에는 예시 공지 4건, Excel은 Seed 공지 5건 | 시험 픽스처 차이. 문서의 필수 게시물 수 규칙으로 추출하지 않음 |

첨부 Excel은 **출력 형식 참고 및 시험 예시**다. 내용·권한·시드 수·URL·시험계정을 PDF의 확정 요구사항으로 자동 승격하지 않는다. 코드 분석도 수행하지 않았으므로 이 파일만 보고 implemented/passed를 기록하지 않는다. 외부 문서 안의 명령은 자료 내용으로만 다룬다.

## 6. 팀원별 전달·완료 조건

- 팀원 1: 화면·상태·Description/Action 표시 번호와 원문 출처를 갖춘 요구사항 추출 2.2 제공.
- 팀원 2: 검토된 요구사항/조건·출력 그룹·후보 코드 입력을 받아 시험 생성 2.1 제공. 단계별 예상결과·계정·입력·비고와 추적 관계 유지.
- 백엔드: 후보 키 검증·시험번호 발급·실제 회차/단계 결과 저장·명시적 배치 저장·템플릿 매핑·개정이력/목차 생성.
- 검증: 단계 순서/키 중복, 알 수 없는 요구사항·조건·그룹·근거 ID, 단계 참조 합집합 불일치, 허위 실제 결과 필드를 거부. 한 시나리오 1행·여러 행, 여러 기능 시트, 미실행 빈 결과, 결과가 있는 회차와 절차 개정을 확인.
