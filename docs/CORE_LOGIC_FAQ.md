# 주요 처리 로직 질문과 현재 구현 범위

2026-10-30 코드 기준. 구현된 동작과 향후 개선 제안을 구분한다.

## 1. 화면 헤더의 의미

여기서 화면 헤더는 서비스 화면 상단 메뉴가 아니라 **업로드한 기획서의 각 페이지 상단에 있는 메타정보 표**다. 현재 템플릿에서 `Depth`, `화면명`, `화면ID`, `작성자`를 읽는다. 예를 들어 공지사항 목록 페이지의 화면 ID는 `NOTICE-001`이다. 문서의 어느 기능·화면을 설명하는 페이지인지 식별하기 위해 사용한다.

## 2. 텍스트 추출과 OCR이 섞이는 이유

PDF의 눈에 보이는 글자가 항상 검색·복사 가능한 텍스트인 것은 아니다. 글자가 이미지 또는 벡터 외곽선으로 들어 있으면 직접 텍스트를 읽을 수 없다. `extract_header()`는 각 값 칸에서 직접 텍스트 추출을 먼저 시도하고, 비어 있을 때만 OCR로 보완한다. 한 페이지 안에서도 필드별 방식이 다를 수 있다. `header_source`에 `text`/`ocr`와 신뢰도를 보존한다.

## 3. OCR과 LLM의 구분

현재 PDF 구조 파싱과 OCR에는 LLM을 쓰지 않는다. `extractor/pdf_screens.py`의 절차는 다음과 같다.

1. PyMuPDF로 상단 라벨과 표의 사각형·좌표를 찾는다.
2. 해당 값 칸에서 직접 텍스트를 읽는다.
3. 읽히지 않으면 그 칸만 이미지로 렌더링한다. 현재 확대 배율은 12배다.
4. Pillow로 이미지를 구성하고 `pytesseract`를 통해 Tesseract를 실행한다. 한글·영어 언어 데이터와 한 줄 인식 설정 `--psm 7`을 사용한다.
5. 텍스트와 인식 신뢰도를 받아 저장한다. OCR 실패·낮은 신뢰도·화면 ID 형식 이상은 검토 대상으로 남긴다.

현재 OCR은 주로 화면 헤더 값 칸을 보완하는 경로다. 본문과 페이지 전체를 OCR한 뒤 모든 문서 형식을 해석하는 범용 기능은 구현되어 있지 않다. 이후 원문을 조건으로 분해하고 코드와 대조하거나 시험을 만드는 단계에는 LLM을 사용한다.

## 4. 요구사항과 수락 조건의 차이

현재 파서는 Description 0·1 등의 행과 Action A·B 등의 행을 각각 원문 요구사항으로 다룬다. 줄바꿈으로 나뉜 같은 행의 본문을 합치며, 서로 무관한 기능을 임의로 합치는 것은 아니다. 기능 소속은 별도의 주제·소주제 구조로 묶는다.

하나의 원문 행에 여러 사실이 들어 있으면 LLM이 개별 판정 단위로 나눈다. 설명용 원문이 `제목은 50자 이하이고 비어 있으면 저장할 수 없다`라면 `제목 최대 50자`와 `빈 제목 저장 차단`을 각각 확인한다. 한 조건은 구현됐고 다른 조건은 틀릴 수 있으므로 분리한다. 이 조건들이 수락 조건이다. 분해된 문장마다 원문 인용을 연결한다.

## 5. 범주의 의미

범주는 수락 조건이 어떤 종류의 확인을 요구하는지 나타내는 분류다. 한 요구사항 안의 조건마다 범주가 다를 수 있다.

| 범주 | 예 |
| --- | --- |
| display | 입력칸 존재, 날짜 표시 형식 |
| validation | 필수 입력, 50자 제한, 형식 검사와 안내 |
| navigation | 화면 이동, 새 창, 확인 팝업 |
| business_logic | 인증, 필터, 조회수 처리 |
| data | 저장·수정·삭제·파일 처리 |
| error_message | 로그인 실패·중복 가입처럼 서버 확인 결과의 메시지 |

범주는 그 조건의 구현 여부나 정적 검증 가능 여부를 뜻하지 않는다. 기능/비기능 요구사항 구분(`req_type`)과도 별도다.

## 6. 코드 스냅샷의 의미

분석할 때 사용한 소스코드의 경로·내용을 특정 시점의 버전으로 서버에 저장한 것이다. VM·디스크 스냅샷이나 Git 커밋을 만드는 기능이 아니다. 지원 소스 파일을 저장하고 파일 내용의 해시로 동일한 버전인지 구분한다. 코드 청크와 분석 결과는 해당 스냅샷 ID를 참조한다.

## 7. 요구사항 개정과 코드 버전을 고정하는 이유

`요구사항 개정 2 + 코드 스냅샷 A`는 그때 저장된 요구사항 버전과 업로드된 코드 버전을 비교했다는 뜻이다.

설명용 예로, 명세가 제목 50자이고 코드 A가 100자를 허용하면 불일치다. 코드를 50자 제한으로 고쳐 다시 업로드하면 새 스냅샷 B로 검증한다. 과거 결과는 코드 A의 100자 구현을 기준으로 한 불일치로 남아야 한다. 요구사항을 수정한 경우도 동일하다. 현재 파일이나 최신 명세로 과거 판정의 기준을 바꾸지 않기 위한 구조다.

## 8. 청크의 단위와 크기

청크는 LLM에 근거 후보로 제공할 코드 조각이다. 크기가 동일한 조각은 아니다.

- Java 클래스는 클래스 전체를 한 청크로 만들지 않는다. 어노테이션·클래스 선언부, 필드 선언, 메서드·생성자 본문을 나눈다.
- JavaScript·JSX의 이름 있는 함수나 함수형 컴포넌트는 통째로 한 청크다. 중첩 함수는 바깥 함수에 포함해 중복을 피한다. 여러 줄 최상위 문장은 별도 청크, 연속된 한 줄 문장은 묶음이 될 수 있다.
- HTML은 form·table·nav 등 의미 블록을 한 청크로 만들고, 확정한 블록 안쪽은 다시 쪼개지 않는다.
- 별도 파서 결과가 없는 지원 소스는 기본적으로 120줄씩 나눈다.

현재 구조 기반 청크에는 균일한 토큰 크기 상한과 큰 함수 자동 재분할이 없다. 긴 메서드·컴포넌트가 큰 청크로 남는 것은 현재 한계다. 검증 전체에는 50만 문자·5000청크 한도가 있지만 큰 청크의 크기를 균일하게 만드는 기능은 아니다.

개선 제안: 구조를 우선 유지하되 큰 함수의 본문은 문장·블록 경계에서 추가로 나누고, 함수 선언·상위 구조·원본 줄 범위를 함께 전달한다. 이 개선은 이번 코드 검증 오류 수정에 포함하지 않았다.

## 9. 정적 분석의 한계와 보완

동적 호출의 한계를 완전히 해결한 상태는 아니다. 현재는 사용자가 화면 진입 파일을 확인하고, 식별자 참조·URL·Spring/React 연결 규칙을 사용해 관계를 추정한다. 다른 화면 코드는 참고 근거로 남기며, 정적 검증 불가나 근거 불충분은 검토 필요로 넘긴다. 그래프는 실제 실행 순서를 측정한 기록이 아니다.

향후에는 테스트 환경의 요청 기록·커버리지·브라우저 동작과 정적 결과를 대조해 보완할 수 있다. 현재 시스템이 대상 서비스를 실행해 이 정보를 자동 수집하는 기능은 구현되어 있지 않다.

## 10. target이 대부분 unknown인 이유와 필요성

현재 자동 추출 어댑터는 `target`을 고정으로 `unknown`으로 넣는다. 원문에서 구현 위치를 자동으로 찾아 값을 채우는 단계는 현재 없다. API에서 수동으로 frontend/backend/both를 지정할 수는 있다.

의도한 역할은 명세가 `서버에서 검사`처럼 구현 위치를 명시했는지 보관하는 메타정보다. 실제 코드에 서버 검증이 존재하는지는 별도의 `server_validation`에 기록한다. `target`으로 근거 코드를 미리 거르지 않는다.

현재 핵심 검증을 위해 이 필드를 반드시 사용할 필요는 없다. unknown은 UI에서 생략할 수 있고, 위치를 활용하지 않는 MVP라면 API 계약 변경 시 선택 필드로 바꾸는 방안을 권한다. 현재 계약은 필수이므로 바로 제거하면 스키마·어댑터·프런트 소비자를 함께 고쳐야 한다. 이번 수정에서 필드를 삭제하지 않았다.

## 11. 정상·오류·경계값만으로 충분한가

이 세 값은 현재 시험의 큰 분류일 뿐, 필요한 시험을 전부 다뤘다는 증거가 아니다. 현재 생성기는 각 조건이 시험 단계에 연결되는지와 미포함 사유를 검사하지만, 각 조건에 필요한 권한·상태·오류 조합이 충분한지는 자동으로 보장하지 않는다.

권장하는 개선은 조건별 시험 전략을 먼저 정하고 필요한 시나리오를 만드는 것이다.

| 요구사항 성격 | 필요한 확인 예 |
| --- | --- |
| 입력 제한 | 유효/무효 입력 그룹, 경계 안쪽·정확값·바깥쪽, 필수 여부에 따른 빈 값 |
| 권한 | 명세에 정의된 역할별 허용·거부, UI와 API 동작 |
| 팝업·이동 | 선택지별 목적지, 닫기·취소, 입력값 유지 여부 |
| 저장·수정·삭제 | 처리 결과, 재조회 시 반영, 실패 시 상태 |
| 목록·검색·페이징 | 데이터 없음, 정렬·필터, 첫·마지막 페이지 |
| 여러 조건의 업무 규칙 | 조건 조합에 따른 결과와 상태 전이 |

입력 동등 분할·경계값·결정 테이블·상태 전이는 서로 다른 시험 설계 관점을 제공한다. 참고: [ISTQB CTFL 4.0.1, 4.2절](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf).

명세 기반 시험과 추가 품질 점검은 구분해야 한다. 원문에 없는 재시도 정책·오류 문구·성능 목표 등을 임의의 기대 결과로 확정하면 안 된다. 추가 시험은 제안 또는 검토 필요로 남겨 승인 후 사용하도록 한다.

현재 `positive`/`negative`/`boundary`는 유지하면서 시험 관점과 적용 사유를 별도 정보로 추가하고, 조건별로 계획한 관점 중 생성된 시험이 무엇을 다뤘는지 검사하는 방식으로 확장할 수 있다. 이 부분은 제안이며 현재 구현된 자동 보장 기능이 아니다.
