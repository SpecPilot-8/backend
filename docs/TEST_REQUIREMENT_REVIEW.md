# 요구사항 대비 시험 설계 검토

갱신일: 2026-10-30

## 무엇을 보고 시험을 만드는가

1. 완료된 검증 실행에 고정한 **승인 요구사항 개정**을 선택한다. 현재 최신 요구사항으로 자동 대체하지 않는다.
2. 선택 요구사항을 소주제별로 묶고 **원문, 수락 조건, 검토 메모, 조건 분류·수치 제한·모호한 내용**을 서버에 설정한 LLM에 전달한다.
3. 서버 규칙이 제안한 시험 관점을 함께 전달한다. LLM이 시나리오, 사전 조건, 단계별 절차·기대 결과·입력값·역할·설계 이유를 만든다. 실제 수행 O/X는 만들지 않는다.
4. 서버는 조건 ID와 개정, 관점 연결, 입력 형식, 누락·중복을 검사한다. 이 검사는 문장의 의미적 충분성을 증명하지 않는다.
5. 코드 판정은 별도의 `prediction`으로 붙인다. 생성기의 기대 결과는 명세 기준이다. 코드 결함을 기대 동작으로 받아들이지 않는다.

실제 구현: `testgen/generate.py`, `testgen/design.py`, `api/v2/test_generation_runner.py`, `adapters/v2_testgen.py`.

## 요구사항을 만족하는 시험인가

세 가지를 구분한다.

| 확인 내용 | 근거 | 화면 표현 |
|---|---|---|
| 조건과 시험이 연결됐는가 | 고정 요구사항 개정·조건 ID와 단계 연결 | 이 시험에 연결 / 다른 시험에 연결 / 시험 연결 없음 |
| 절차·입력값·기대 결과가 조건을 적절히 확인하는가 | 사람이 원문과 시험을 비교하고 남긴 설계 판단·사유 | 설계 적합 / 보완 필요 / 판단 보류 / 미검토 |
| 실제 프로그램이 조건을 충족하는가 | 해당 절차를 실행하고 기록한 실제 결과 | 미실행 / 통과 / 실패 / 보류 |

예를 들어 요구사항이 ‘제목은 최대 50자, 초과하면 저장 불가’라면 50자 허용·51자 거부를 따로 확인하는 절차인지, 다른 필수 입력은 유효하게 준비하는지, 기대 결과가 저장 허용/거부를 구체적으로 표현하는지 검토한다. ‘제목 입력 후 정상 동작’처럼 관찰할 결과가 모호하면 조건 ID가 연결돼 있어도 보완이 필요하다.

수락 조건 전체가 시험에 연결돼 있어도 필요한 경계·상태·권한 조합까지 충분하다는 뜻은 아니다. 원문에 없는 정책은 명세 보완으로 확인하고 시험을 추가한다. 현재 별도의 의미적 적합성 AI 판정기는 호출하지 않는다. 설계 검토는 사람의 판단 기록이다.

## 옆 대조 패널

시험 상세 옆에서 고정 개정의 **요구사항 원문 전체와 모든 수락 조건**을 표시한다. 선택 시험이 일부 조건만 담당해도 나머지 조건을 숨기지 않는다. 다른 시험에 연결된 조건은 해당 단계로 이동하고, 연결이 없으면 시험 보완을 안내한다. ‘사양서 전체’로 선택 범위 밖 요구사항도 확인할 수 있다.

각 조건 아래에 해당 시험 단계의 절차·명세 기대 결과·AI 설계 설명을 표시하고 PDF 원문으로 연결한다. 원문 누락이나 다른 개정은 경고하며 과거 개정을 최신 데이터로 대신하지 않는다. 변경 전 AI 설명과 저장 전 절차는 재검토 대상으로 표시한다.

## 설계 검토 API

`GET /api/v2/projects/{p}/test-cases/{tc}/design-review?revision=1`

해당 시험 절차 개정에 저장된 검토를 반환한다. 없으면 `version:0`, `items:[]`, `status:pending`이다. `origin:manual`이며 요약은 **그 시험에 연결된 조건**만 집계한다. 조건이 모두 `adequate`여야 해당 시험의 status가 `adequate`다. 이것을 사양서 전체 충족으로 해석하지 않는다.

`PUT /api/v2/projects/{p}/test-cases/{tc}/design-review`

```json
{
  "test_case_revision": 1,
  "base_version": 0,
  "client_review_id": "8438ef21-f645-414f-8334-e6c5a91dca12",
  "items": [{
    "requirement_id": "실제 요구사항 ID",
    "requirement_revision": 2,
    "condition_id": "해당 시험에 연결된 실제 조건 ID",
    "decision": "adequate",
    "reason": "다른 필수 입력을 유효하게 준비하고 50자 허용·51자 거부를 비교해 제목 상한을 확인한다."
  }]
}
```

- decision: `adequate`, `needs_changes`, `uncertain`. reason은 공백 불가·최대 2,000자다.
- 부분 조건 저장은 기존 검토와 합친다. 연결하지 않은 조건·다른 요구사항 개정·중복 조건은 422다.
- 오래된 시험 절차는 409 `CASE_REVISION_CHANGED`, 동시 검토 수정은 409 `VERSION_CONFLICT`다. 기존 입력을 보존하고 최신값을 확인한다.
- 같은 client_review_id와 같은 요청의 재전송은 기존 응답을 반환한다. 다른 내용이면 409 `IDEMPOTENCY_CONFLICT`다.
- 시험 절차를 수정하면 새 개정은 미검토로 시작한다. 이전 검토는 이전 revision 조회로 남으며 실제 수행 기록과 사양서 개정을 바꾸지 않는다.
- `test_design_review` 리소스와 불변 수정 이력을 사용하므로 새 DB 테이블이 필요하지 않다. 현재 사용자 인증이 없는 환경에서는 검토자의 신원을 보증하지 않으며 `manual` 기록으로 취급한다.

## Excel

`include_analysis_detail=true`의 **요구사항·시험 대응** 시트에 요구사항 원문 전체·수락 조건·시험/단계·절차·명세 기대 결과·AI 설명·사람의 설계 판단과 사유를 함께 출력한다. 연결되지 않은 조건도 행으로 남긴다. 원문이 없으면 ‘원문 미등록’으로 표시한다.

출력 시 시험 개정과 검토 리소스 버전을 선택 정보에 기록한다. 다운로드 파일은 이후 검토 수정으로 바뀌지 않는다. 기본 10열 시험표와 실제 O/X 의미는 유지한다.
