## 1. 왜 필요한가

판정 결과 상태 6개의 이름은 정해져 있지만, 어떤 경우에 어떤 상태를 붙이는지 경계가 없다.
경계가 없으면 판정 로직의 기준과 골든셋(정답 라벨)의 기준이 따로 논다. 같은 요구사항을 두고
사람마다 다른 라벨을 붙이면 정확도를 잴 수 없다.

이 문서의 사례는 모두 실제 매칭 결과에서 나왔다.

| 실행 | 레포 | 방식 | 모델 |
|---|---|---|---|
| run 4 | spring-sample | full_context | claude-opus-5 |
| run 5 | react-sample | full_context | claude-opus-5 |

근거 옆의 태그는 `scripts/tag_scope.py`가 붙인 화면 범위상 위치다.

- `this_screen`: 요구사항이 속한 화면에서 도달하는 코드
- `other_screen`: 다른 화면에서만 도달하는 코드
- `unreachable`: 어느 화면에서도 도달하지 못하는 코드 (쓰이지 않는 코드 후보)

## 2. 상태 정의 (초안)

| 상태 | 정의 | 필요한 근거 |
|---|---|---|
| `implemented` | 요구사항의 모든 조건이 기획서대로 구현됨 | 조건마다 `this_screen` 근거가 있고 값·동작이 기획서와 일치 |
| `partial` | 조건 중 일부만 구현됨. 구현된 조건은 기획서와 일치 | 일부 조건에만 근거가 있음 |
| `mismatch` | 구현은 됐으나 값·동작·위치가 기획서와 다름 | 근거가 있고, 기획서와 다른 점을 근거로 지목할 수 있음 |
| `not_found` | 이 화면에서 동작하는 구현이 없음 | `this_screen` 근거가 없음 (다른 곳의 코드만 있는 경우 포함, Q5 참고) |
| `needs_review` | 근거는 있으나 자동으로 판정할 수 없음 | 근거가 있으나 판정 불가. LLM 출력 검증 실패 포함 |
| `not_statically_verifiable` | 정적 분석으로 확인할 수 없는 요구사항 | 판정을 시도하지 않음 (원칙4의 `verifiable` 축) |

`partial`과 `mismatch`가 동시에 해당할 때(일부는 없고 일부는 다름)는 **`mismatch`가 우선**한다.
다른 부분이 있다는 사실이 더 중요한 정보이기 때문이다. (제안. Q0 결정에 따라 달라짐)

**구조적 보장 (2026-09-29 추가):** 명시적인 검사 코드가 없어도 구조상 조건이 항상 지켜지면 `implemented`다.
사례: "게시일자는 미래일 수 없다"는 두 스택 모두 게시일자가 글 저장 시각이라 미래가 될 수 없다. 검사 코드를
찾느냐에 따라 Spring은 `implemented`, React는 `not_found`로 갈렸다.

## 3. 결정이 필요한 질문

### Q0. 판정 단위: 요구사항 번호 하나 vs 그 안의 하위 조건

**사례: NOTICE-001-1** (공지 목록 표시 조건)

요구사항 번호는 하나인데 원문 안에 조건이 열 개가 넘는다.

- (1) 게시일자 최신순
- (2)(3) 게시기간·게시여부 OFF 글 숨김
- (4) 프론트 화면에서 삭제 불가
- 컬럼 5개 각각의 정렬·포맷 (게시일자 YYYY/MM/DD 등)
- 조회수 유저당 +1
- 빈 목록일 때 "데이터가 없습니다" 표시

run 4는 이 한 항목에 근거 17개를 골랐다. 조회수 증가 함수나 삭제 함수처럼 언뜻 무관해 보이는 것도
(4)·(5) 조건의 근거였다. 요구사항 번호 단위로 판정하면 이 항목은 거의 항상 `partial` 아니면
`mismatch`가 되고, **어느 조건이 문제인지** 결과에서 보이지 않는다.

| 선택지 | 의미 | 영향 |
|---|---|---|
| A. 번호 단위 | 기획서 번호(0, 1, A, B ...) 하나에 상태 하나 | 구현이 단순함. 복합 요구사항은 결과가 뭉개짐 |
| B. 하위 조건 단위 | 원문의 (1)(2)… 항목마다 판정하고 번호 단위 상태는 집계 | 테스트 사양서의 세부 단계(59개)와 단위가 맞음. 하위 조건 분해 단계가 추가됨 |

**제안: B.**
- 출력 양식(테스트 사양서)이 이미 세부 단계 단위다 (CLAUDE.md 7.3).
- 원문이 (1)(2) 번호로 조건을 나누고 있어 분해를 상당 부분 규칙으로 할 수 있다 (7.1).

B로 가면 번호 단위 집계 규칙도 정해야 한다. 초안은 다음과 같다.
하나라도 `mismatch` → `mismatch` / 일부 `not_found` → `partial` / 전부 `not_found` → `not_found`.

**결정 (잠정):** B. 하위 조건 단위

### Q1. "~화면으로 이동한다" 요구사항의 근거

**사례: LOGIN-001-D** "비밀번호찾기화면(LOGIN-003)이 표시된다"

| 근거 (run 4) | 태그 |
|---|---|
| `login.html` 로그인 화면의 링크 | this_screen |
| `AuthController.passwordForgot` 이동 대상 화면의 컨트롤러 | other_screen (LOGIN-003) |
| `password-forgot.html` 이동 대상 화면 | other_screen (LOGIN-003) |

기준선은 이동 대상 화면의 코드도 근거로 고른다. 범위 밖으로 떨어진 근거 중 가장 많은 유형이다.

| 선택지 | 의미 |
|---|---|
| A. 출발 쪽만 | 이 화면의 링크·버튼·리다이렉트가 올바른 목적지를 가리키면 `implemented`. 목적지 화면의 구현은 그 화면의 요구사항에서 따로 판정 |
| B. 목적지까지 | 목적지 화면이 실제로 존재하고 열려야 `implemented` |

**제안: A.**
- 목적지 화면은 그 화면의 요구사항으로 따로 판정된다. B로 하면 같은 결함이 두 번 집계된다.
- 목적지 URL이 존재하는지 정도는 규칙으로 확인할 수 있다. 존재하지 않으면 `mismatch`로 둔다.

**결정 (잠정):** A. 출발 쪽만

### Q2. 기획서와 다른 화면에 구현된 기능

**사례: NOTICE-005-B** "(수정화면의 삭제 팝업에서) 삭제하고 목록으로 이동한다"

- 기획서: 수정화면 → 삭제 버튼 → 확인 팝업 → 삭제
- Spring: 상세화면에서 확인 없이 즉시 삭제 (CLAUDE.md 8.3)
- React: 상세화면에서 삭제

| 근거 | 태그 |
|---|---|
| `NoticeController.delete`, `NoticeService.deleteNotice`, `detail.html` 삭제 폼 (run 4) | other_screen (NOTICE-006) |
| `NoticeDetailPage`, 삭제 API·라우트·서비스 (run 5) | other_screen (NOTICE-006) |

| 선택지 | 의미 |
|---|---|
| A. `mismatch` | 기능은 있으나 위치(와 흐름)가 기획서와 다름 |
| B. `partial` | 삭제 자체는 되지만 기획된 흐름 일부가 없음 |
| C. `not_found` | 기획된 화면에는 없음 |

**제안: A.**
- 사용자는 기획서의 경로로 삭제할 수 없으니 `implemented`는 아니다.
- 삭제 기능이 있다는 사실은 결과에 남아야 하므로 `not_found`도 아니다.
- 확인 팝업이 빠진 부분은 Q0-B로 가면 하위 조건에서 따로 `not_found`로 드러난다.

**결정 (잠정):** A. `mismatch`

### Q3. 화면 요소만 있고 동작이 없는 기능

**사례: LOGIN-001-A** "Google 로그인 화면이 새 창으로 표시된다" (소셜 로그인)

| 근거 | 태그 |
|---|---|
| `login.html` 로그인 버튼 영역, `SecurityConfig.securityFilterChain` (run 4) | this_screen |
| `LoginPage` (run 5) | this_screen |

버튼은 있으나 클릭 시 동작이 없다 (CLAUDE.md 8.2). 근거가 `this_screen`이라 태그만으로는 걸러지지 않는다.

| 선택지 | 의미 |
|---|---|
| A. `not_found` | 동작 요구사항(Action/Event)은 동작을 수행하는 코드가 있어야 근거로 인정 |
| B. `partial` | 버튼이 있으니 일부 구현 |

**제안: A.**
- "근거 존재 ≠ 구현" (CLAUDE.md 8.2).
- 버튼 표시 요구사항(LOGIN-001-1 "로고를 포함한 버튼으로 표시")은 별개 번호라서 그쪽에서 `implemented`가 된다.
- 동작 요구사항까지 `partial`로 두면 "버튼만 있는 기능"이 결과에서 드러나지 않는다.

**결정 (잠정):** A. `not_found`

### Q4. 근거가 다른 화면 코드나 쓰이지 않는 코드뿐인 경우

**사례: MYPAGE-001-C** "(비밀번호 입력란) 클릭 시마다 눈 아이콘이 반전된다"

| 근거 | 태그 | 실제 |
|---|---|---|
| `auth.js` 비밀번호 토글 스크립트 (run 4) | other_screen | 마이페이지는 `auth.js`를 불러오지 않음 |
| `mypage/password.html` 폼 (run 4) | unreachable | 어떤 컨트롤러도 반환하지 않는 템플릿 |
| `mypage/index.html` 섹션 (run 4) | this_screen | 토글 없음 |
| `PasswordInput` 컴포넌트 (run 5) | other_screen | MyPage는 이 컴포넌트를 쓰지 않음 |
| `LoginPage` (run 5) | other_screen | 로그인 화면의 토글 |
| `MyPage` (run 5) | this_screen | 일반 password 입력칸만 있음 |

두 스택 모두 마이페이지에는 토글이 없는 것으로 보인다(실행 검증 전).
전체 투입 방식이 레포 다른 곳의 토글 코드를 근거로 골랐다. 이 근거를 그대로 믿으면 `implemented` 오판이 난다.

**태그만으로는 이 사례를 거르지 못한다.** 토글이 없는 `mypage/index.html` 섹션과 `MyPage`가
`this_screen` 근거로 함께 뽑혔다. "이 화면 근거가 하나도 없으면 not_found" 규칙으로는 안 걸린다.
실제로 `this_screen` 근거가 하나도 없는 요구사항은 두 실행 합쳐 3건뿐이었다
(run 4 NOTICE-004-E, run 5 NOTICE-004-E·NOTICE-005-0. 모두 Q2의 삭제 사례).

| 선택지 | 의미 |
|---|---|
| A. 태그로 거름 | `this_screen` 근거가 없으면 `not_found`. 위 사례는 못 거름 |
| B. 근거 역할 분리 | 구현 여부는 `this_screen` 근거만 보고 판단. `other_screen` 근거는 "다른 곳에 비슷한 코드 있음"이라는 참고로만 판정에 넘김. `unreachable`은 근거에서 제외. `this_screen` 근거가 없고 `other_screen`만 있으면 `needs_review` |
| C. LLM에 맡김 | 태그를 판정 프롬프트에 넘기고 LLM이 알아서 결정 |

A는 Q2와도 충돌한다. Q2의 삭제도 `other_screen` 근거뿐인데 제안은 `mismatch`였다.
규칙으로는 "다른 화면에 **같은 기능**이 구현됨"(Q2)과 "다른 화면의 **비슷한 코드**를 잘못 고름"(Q4)을
구분하지 못한다.

**제안: B.**
- 위 사례에서 판정은 `index.html`과 `MyPage`만 보고 토글이 없다고 판단해야 한다. `auth.js`, `PasswordInput`은 "다른 화면에 있음"으로만 표시한다.
- `other_screen`만 있는 요구사항(이번에 3건)은 Q2 유형인지 Q4 유형인지 사람이 가린다. 원칙3(사람 검수는 의심 구간만)에 해당한다.
- `unreachable`은 쓰이지 않는 코드라 근거로 인정하지 않는다.

**보완 (2026-09-29):** 조건 단위 판정에서도 같은 기준을 쓴다. 이 화면 근거에는 없고 다른 화면 코드에 같은
기능이 있으면 `not_found`가 아니라 `needs_review`다. 사례: "게시물을 열람하면 조회수가 올라간다"는 목록 화면
(NOTICE-001) 요구사항이지만 증가 코드는 두 스택 모두 상세화면에 있다.

**결정 (잠정):** B. 근거 역할 분리

### Q5. 에러 메시지 문구가 기획서와 다른 경우

**사례:** 에러 메시지 문구가 전반적으로 기획서와 다름 (CLAUDE.md 8.3)
LOGIN-002-C 기획서 "이미 가입된 이메일입니다. 입력한 이메일을 확인해주세요." → 코드 검색 0건

| 선택지 | 의미 |
|---|---|
| A. `mismatch` | 문구가 다르면 불일치 |
| B. 의미 같으면 `implemented` | 같은 조건에서 에러를 보여주면 구현으로 봄 |
| C. 분리 | 동작(조건에서 에러 표시)으로 상태를 정하고, 문구 일치 여부는 별도 속성으로 기록 |

**제안: C.**
- A로 하면 에러 메시지가 들어간 요구사항이 거의 전부 `mismatch`가 되어 진짜 동작 불일치가 묻힌다.
- B로 하면 문구 차이가 결과에서 사라진다. 발주사가 문구를 요구사항으로 볼 수도 있다.
- C는 두 정보를 다 남긴다. 판정 결과에 `message_match` 같은 필드를 추가해야 한다 (API 응답의 판별 유니온에도 반영, 10장).

**보완 (2026-09-29):** 기획서가 경우마다 다른 메시지를 요구하는데 코드가 그 경우를 구분하지 못하면,
문구 문제가 아니라 동작 차이이므로 `mismatch`다. 사례: LOGIN-003-A는 "등록된 이메일 없음"과 "이름 불일치"를
다른 메시지로 요구하지만, 코드는 이메일과 이름을 한 번에 조회해 공통 메시지 하나만 보여준다 (CLAUDE.md 8.3).

**결정 (잠정, 씽크트리 확인 필요):** C. 분리

### Q6. 화면에만 검증이 있고 서버 검증이 없는 경우

**사례: NOTICE-002-1** "제목은 50자까지 입력할 수 있다. 50자가 넘어가면 입력을 할 수 없으며…"

| | 근거 |
|---|---|
| Spring (run 4) | `form.html` 폼, `notice-form.js` 글자 수, `NoticeForm#title` (`@Size` 서버 검증) |
| React (run 5) | `NoticeFormPage`, `validateNoticeForm` — 서버 쪽 길이 검증 없음 (CLAUDE.md 8.1) |

| 선택지 | 의미 |
|---|---|
| A. `implemented` | 기획서 문구("입력할 수 없다")는 화면 동작이므로 화면 검증으로 충족 |
| B. `partial` | 서버 검증이 없으면 일부 구현 |
| C. A + 위험 표시 | `implemented`로 두되 "서버 검증 없음"을 별도 표시 |

**제안: C.**
- 기획서는 화면 동작만 요구한다. 서버 검증을 요구사항으로 추가 해석하면 기획서에 없는 기준으로 판정하게 된다.
- 다만 API로 직접 요청하면 우회된다는 점은 발주사에 유용한 정보라 버리지 않는다.

**결정 (잠정, 씽크트리 확인 필요):** C. A + 위험 표시

### Q7. 기획서가 틀렸거나 옛 버전을 따른 경우

**사례:**
- NOTICE-004-D 기획서 "저장 후 목록(NOTICE-001)으로 이동" → 코드는 상세로 이동. 옛 기획 버전을 따른 것으로 보임 (CLAUDE.md 8.3)
- 기획서 오타: `게이 종료일`(NOTICE-002-3), `청부파일`, 잘린 문장, 앞뒤 모순 (7.2)

| 선택지 | 의미 |
|---|---|
| A. `mismatch` | 기획서가 기준. 어느 쪽이 맞는지는 판정하지 않음 |
| B. 새 상태 `spec_issue` | 기획서 결함으로 분류 |
| C. A + 원인 표시 | `mismatch`로 두되, 기획서 쪽 의심 사유를 별도 필드로 남김 |

**제안: C.**
- 도구는 어느 쪽이 맞는지 알 수 없다. 기획서가 판정 기준이라는 전제를 유지한다.
- 상태를 늘리면 API·프론트·평가 지표가 모두 영향받는다.
- 오타는 파싱 단계의 검수 큐에서 걸러질 대상이다(원칙3). 판정 상태로 다룰 문제가 아니다.

**결정 (잠정, 씽크트리 확인 필요):** C. A + 원인 표시

### Q8. `not_statically_verifiable`의 경계

**사례:**
- NOTICE-001-B "선택된 메뉴는 배경색 Navy, 글자색 White"
- NOTICE-002-2 "게시시작일을 클릭하면 캘린더가 표시되며, 날짜를 선택하면 캘린더가 없어진다"

| 선택지 | 기준 |
|---|---|
| A. 시각·런타임 전부 | 색·정렬·크기 같은 시각 스타일, 캘린더·파일 탐색기처럼 브라우저가 제공하는 동작은 전부 검증 불가. 요소·팝업이 있는지와 그 문구, 클릭에 따른 표시 전환은 코드로 확인 |
| B. 코드에 값이 있으면 검증 가능 | CSS 색상값이나 `<input type="date">`처럼 코드에서 확인할 수 있는 것은 검증 대상 |

B로 가면 CSS도 청킹 대상에 넣어야 한다 (현재 제외, README 알려진 한계).

**제안: A로 시작.**
- 현재 파이프라인에 CSS가 없다.
- 브라우저 기본 위젯(캘린더)의 동작은 코드만으로 보장되지 않는다.
- 해당 요구사항이 몇 건인지 세어 보고, 많으면 B를 재검토한다.

**결정 (잠정):** A. 시각·런타임 전부 검증 불가

## 4. 판정 순서 (잠정 결정 기준)

```
1. verifiable = not_statically_verifiable      → not_statically_verifiable (판정 시도 안 함)
2. LLM 출력 검증 실패 (match_issue 존재)          → needs_review
3. this_screen 근거 없음
     other_screen 근거만 있음                    → needs_review        (Q4-B)
     unreachable 근거만 있거나 근거 없음          → not_found
   이후 단계는 this_screen 근거로만 판단. other_screen은 참고로만 넘김 (Q4-B)
4. 동작 요구사항인데 동작 코드가 없음(요소만 있음) → not_found           (Q3-A)
5. 근거로 값·동작·위치를 기획서와 비교
     다른 점이 하나라도 있음                      → mismatch            (Q2, Q7)
     일부 조건만 있음                            → partial
     전부 있고 일치                              → implemented
   문구 일치 여부, 서버 검증 유무는 상태와 별도 필드로 기록 (Q5-C, Q6-C)
```
