# SpecPilot 기능명세서

작성 기준일: 2026-10-09

SpecPilot은 기획서의 요구사항을 소스코드와 대조하고, 판정 근거·요구사항 추적표·테스트 사양서를 제공하는 도구다.
이 문서는 MVP의 목표 기능, 입력·출력, 완료 조건과 현재 구현 범위를 정의한다.
워크스페이스의 `SpecPilot_필수_상세기능_및_UI명세서.md`를 바탕으로 백엔드 연동 계약을 구체화했다.

## 1. 적용 범위와 문서 읽는 기준

- 한국어 기획서의 DOCX·PDF·XLSX를 대상으로 한다. 일본어 번역과 원문·번역본 매핑은 제외한다.
- MVP에서는 선정한 모델 하나로 요구사항 구조화·체크리스트 분해·검증·테스트 생성을 처리한다.
  제공자와 구체적인 모델명은 PoC에서 확정하며, 단계별로 다른 모델을 배정하지 않는다.
- 다중 모델은 후속 확장이다. 지원하는 제공자별 어댑터·프로필을 추가한 뒤 키를 바꿔 전환할 수 있도록 설계한다.
  API 키만으로 미지원 제공자나 임의 모델을 자동 인식하지 않는다.
- 회원가입·사용자 인증, 자동 테스트 실행, 운영 배포, MCP 서버 전송 계층은 이번 API MVP에서 제외한다.
- FastAPI 백엔드는 데이터와 분석 작업을 관리한다. VS Code 확장은 화면·코드 이동·진단 표시·수정 적용을 담당한다.

**목표 기능과 구현 완료는 구분한다.** 아래 완료 조건은 최종 MVP가 갖춰야 할 동작이다.
현재 API는 AI 실행 어댑터를 연결하지 않았으며, 해당 요청에서 누락 기능을 명시한다.

현재 구현 상태 표는 전체 구현을 포함하는 `feat/llm-settings-api` 브랜치 기준이다.
작성 시점의 `main`에는 서버·프로젝트·작업 조회 기반만 반영되어 있다. 후속 기능 PR은 앞선 기능 브랜치로
병합되어 있으므로, `main`에서 전체 기능을 사용하려면 후속 변경의 통합이 필요하다.
실제 실행 중인 서버의 제공 기능은 `GET /api/v1/capabilities`로 확인한다.

## 2. 사용자 시나리오

### 목표 흐름

1. 프로젝트와 로컬 워크스페이스를 등록하고 선정 모델의 연결을 설정한다.
2. 기획서를 업로드하고 원문·위치 정보와 구조화된 요구사항을 확인한다.
3. 검증할 백엔드 또는 프론트엔드 파일·폴더를 선택하고 코드 스냅샷을 만든다.
4. 요구사항과 체크리스트를 코드에 대조한다. 관련 파일·라인·코드·판정 이유를 확인한다.
5. 불일치·부분구현의 수정 제안을 검토하고 확장에서 적용한 뒤 다시 검증한다.
6. 요구사항 추적 대시보드와 테스트 케이스를 검토하고 XLSX를 다운로드한다.

### AI 미연결 상태의 현재 흐름

문서 텍스트 추출 → 요구사항·체크리스트 수동 등록 → 코드 인덱싱 → 수동 판정·근거 등록 →
진단·대시보드·추적표 조회 → 테스트 케이스 수동 등록 → XLSX 출력이 가능하다.
AI 요청은 작업 접수만 수행하며, `blocked` 또는 `501`과 `missing_features`를 반환한다.

## 3. 상세 기능 명세

### F-00. 단일 모델 연결 설정

| ID | 기능 | 입력 | 출력 | 완료 조건 |
|---|---|---|---|---|
| F-00-1 | 단일 모델 설정 | 프로젝트, 제공자, 모델명, 선택적 접속 주소 | 모델 설정·설정 버전 | 프로젝트마다 설정 하나를 사용하고 각 분석 작업의 설정을 시작 시 고정한다 |
| F-00-2 | API 키 등록·교체 및 연결 확인 | 선정 모델의 API 키 | 연결 성공 여부·실패 사유 | 키는 확장의 SecretStorage에 보관한다. 서버 DB·작업·응답·로그·Excel에 키를 남기지 않는다 |
| F-00-3 | 공통 모델 호출 | 원문 또는 코드, 단계별 프롬프트·응답 스키마 | 검증된 구조화 응답 | 추출·검증·테스트 생성이 같은 모델 설정을 사용하며 응답 형식과 참조 ID를 검증한다 |

현재는 키를 제외한 설정 저장과 버전 고정만 구현했다. 연결 확인 API는 `501`이며 실제 LLM 호출은 미연결이다.

### F-01. 기획서 분석 및 요구사항 구조화

| ID | 기능 | 입력 | 출력 | 완료 조건 |
|---|---|---|---|---|
| F-01-1 | 기획서 업로드·텍스트 추출 | DOCX·PDF·XLSX와 프로젝트 ID | 저장된 문서, 원문, 블록·표·위치, 경고 | 문서 순서와 추출 가능한 위치를 보존한다. 읽지 못한 내용은 성공한 요구사항으로 만들지 않는다 |
| F-01-2 | 요구사항 구조화 | 문서 원문·블록 | 표시 ID, 기능명, 조건, 처리, 기대결과 | 원문에 근거한 요구사항을 분리하며 요구사항의 서버 UUID와 표시용 ID를 구분한다 |
| F-01-3 | 역할별 체크리스트 분해 | 개별 요구사항 | 백엔드·프론트엔드 체크리스트 | 하나의 요구사항을 실제 코드로 확인 가능한 항목으로 분해하고 검증 대상을 구분한다 |
| F-01-4 | 요구사항 검토·수정 | 요구사항과 체크리스트 수정 내용 | 수정된 명세·버전 | 명세가 변경되면 버전을 올리고 이전 버전의 판정을 현재 결과에 섞지 않는다 |

백엔드 체크리스트는 API 규격, 입력 검증, 비즈니스 조건, 데이터 변경, 예외·오류 응답을 포함한다.
프론트엔드 체크리스트는 화면 렌더링, 입력 검증, API 요청, 안내·오류 메시지를 포함한다.
현재 자동 구조화·분해는 미연결이며, 같은 데이터 구조로 수동 등록·수정·조회할 수 있다.

문서 위치 표현은 형식에 따라 다르다. DOCX는 본문 순서와 표 행·셀 내용, PDF는 페이지와 좌표,
XLSX는 시트·셀 주소를 제공한다. DOCX 렌더링 페이지, 도형·텍스트박스, OCR, PDF 표 셀 복원은 미지원이다.

### F-02. 소스코드 분석 및 정합성 판정

| ID | 기능 | 입력 | 출력 | 완료 조건 |
|---|---|---|---|---|
| F-02-1 | 검증 대상 코드 입력 | 등록된 워크스페이스 안의 상대 파일·폴더 경로 | 스냅샷, 코드 청크, 파일·줄 번호 | 분석 시점의 코드를 보존하고 같은 입력을 다시 인덱싱해도 청크 ID와 기존 근거를 유지한다 |
| F-02-2 | 코드 호출 흐름 분석 | 요구사항·코드 컨텍스트 | 함수·계층 간 호출 흐름과 근거 위치 | 백엔드의 Controller→Service→Mapper, 프론트엔드의 Component→EventHandler→API 요청 같은 연결을 근거와 함께 제공한다 |
| F-02-3 | 정합성 판정·근거 추출 | 요구사항 버전, 체크리스트, 코드 스냅샷 | 판정 상태, 이유, 근거 배열 | 실제 청크에서 파일·줄 번호·코드를 조회한다. 근거 존재만으로 구현 완료를 판정하지 않는다 |
| F-02-4 | 수정 제안 | 불일치·부분구현 판정과 근거 | 추천 수정 코드 | 해당 기획 조건에 맞는 제안을 제공하고, 적용 후 새 스냅샷에서 재검증한다 |

목표는 코드 유형에 맞는 체크리스트를 자동 매칭하는 것이다. 현재는 코드 저장·조회와 수동 판정을 지원하며
자동 매칭·호출 흐름·판정·수정 제안 생성은 연결하지 않았다. 서버는 코드 파일을 직접 수정하지 않는다.
수동 수정 제안의 조회가 실제 자동 수정 적용을 의미하지 않는다.

### F-03. 테스트 사양서 생성 및 출력

| ID | 기능 | 입력 | 출력 | 완료 조건 |
|---|---|---|---|---|
| F-03-1 | 테스트 케이스 생성 | 요구사항과 코드 검증 결과 | 정상·오류·경계값 케이스 | 유형, 사전조건, 절차, 입력값, 기대결과를 포함하고 요구사항 버전에 연결한다 |
| F-03-2 | 불일치 주의사항 | 현재 스냅샷의 불일치 판정 | 테스트 검토 가이드·비고 | 기획과 코드의 차이를 설명한다. 실제 실행하지 않은 테스트를 실패했다고 단정하지 않는다 |
| F-03-3 | XLSX 다운로드 | 등록되거나 생성된 테스트 케이스 | 실제 Excel 파일 | Test ID, 요구사항 ID, 시나리오, 유형, 사전조건, 절차, 입력값, 기대·실제결과, 판정, 비고를 제공한다 |
| F-03-4 | 테스트 검토·결과 입력 | 수동 수정 내용·실제결과·PASS/FAIL | 수정된 케이스 | 자동 실행이 없는 상태에서는 사람이 입력한 실제결과와 판정만 저장한다 |

현재 AI 테스트 생성은 미연결이다. 수동 등록한 케이스를 출력하며, 케이스가 없으면 오류와 생성기 미연결 사유를 반환한다.
Excel 판정은 기본적으로 비어 있고 PASS/FAIL 선택을 제공한다. 선택한 스냅샷의 불일치 사유는 비고에 추가한다.
고객 견본과 세부 서식을 일치시키는 작업은 별도로 남아 있다.

### F-04. 프로젝트·작업·조회 및 VS Code 연동

| ID | 기능 | 입력 | 출력 | 완료 조건 |
|---|---|---|---|---|
| F-04-1 | 프로젝트 등록·조회 | 프로젝트명·워크스페이스 경로 | 프로젝트 UUID·목록·상세 | 허용 루트 안의 디렉터리만 등록하며 다른 프로젝트의 데이터 참조를 차단한다 |
| F-04-2 | 작업 접수·상태 조회 | 분석 요청·작업 ID | 작업 상태, 설정 스냅샷, 누락 기능, 조회 주소 | 장시간 AI 실행을 동기 성공 응답으로 위장하지 않고 작업 단위로 관리한다 |
| F-04-3 | 요구사항 탐색·코드 이동 | 요구사항 선택 | 상세 체크리스트·근거 파일·줄 번호 | 확장에서 근거 위치로 이동하고 원문·실제 코드·판정 이유를 확인할 수 있다 |
| F-04-4 | 진단·문제 패널 | 현재 요구사항 버전과 스냅샷 | 불일치·부분구현 진단 목록 | VS Code의 0 기반 위치를 사용한다. 이전 버전의 결과를 현재 문제로 표시하지 않는다 |
| F-04-5 | 대시보드·요구사항 추적표 | 프로젝트와 선택적 스냅샷 | 상태별 건수·구현률·추적표·XLSX | 구현률의 분모는 전체 요구사항으로 하고 미분석을 별도 표시한다 |

현재 SSE는 접수된 `blocked` 작업 상태 이벤트 한 번을 전송하고 종료한다. 실행 워커·자동 재시도는 없다.

## 4. VS Code 화면 요구사항

이 절은 확장의 목표 동작이다. 백엔드의 조회 API 구현이 확장 화면 구현 완료를 의미하지 않는다.

| 영역 | 표시 내용 | 주요 동작 |
|---|---|---|
| 좌측 SpecPilot 사이드바 | 업로드·검증·대시보드·사양서 버튼, 요구사항 트리, 선택 항목의 체크리스트 | 요구사항 선택, 근거 코드 위치로 이동, 작업 상태 확인 |
| 메인 코드 에디터 | 호출 흐름, 불일치 표시, 원문·실제 코드·판정 이유 호버, 수정 제안 | 근거 위치 이동, 제안 검토·적용, 재검증 |
| 하단 문제 패널 | 불일치·부분구현 진단 목록 | 진단 클릭 시 코드로 이동 |
| 보조 Webview | 대시보드·추적표, 테스트 케이스 미리보기 | 요구사항 필터·검색, 테스트 검토·수정, Excel 다운로드 |

확장은 파일이 변경되면 이전 스냅샷의 진단을 현재 결과로 확정하지 않고 다시 인덱싱·검증해야 한다.
UI, SecretStorage 연동, 코드 수정 적용은 백엔드 외의 후속 작업이다.

## 5. 공통 데이터와 판정 규칙

| 항목 | 규칙 |
|---|---|
| 식별자 | `id`는 서버 UUID, `req_id`는 `REQ-001` 같은 표시 ID다 |
| 버전 | 판정은 요구사항 `revision`과 코드 `snapshot_id`에 묶는다 |
| 근거 | `evidence`는 항상 배열이며 입력 청크 ID가 선택한 프로젝트·스냅샷에 속하는지 확인한다 |
| 위치 | 근거 경로·줄 번호·코드는 저장된 청크에서 조회한다. LLM이 임의 위치를 생성하지 않는다 |
| 출처 | 수동 판정·테스트는 `source: manual`로 표시한다 |
| 미분석 | `status: null`, `analysis_state: not_run`으로 표시하며 코드 미발견과 구분한다 |
| 통계 | 분석률과 구현률을 별도로 제공하고 미분석을 제외해 구현률을 높이지 않는다 |
| 저장소 | API의 `api_*` 테이블은 기존 CLI 샘플 분석 테이블과 분리한다 |

| 상태 코드 | 표시 의미 |
|---|---|
| `implemented` | 요구사항 구현 |
| `partial` | 일부 조건·처리·예외 누락 |
| `mismatch` | 기획과 다른 값 또는 동작 |
| `not_found` | 관련 코드 미발견·미구현 후보 |
| `needs_review` | 직접 확인 필요 |
| `not_statically_verifiable` | 정적 코드 분석으로 검증 불가능 |

주요 5단계 판정에 더해 정적 검증 불가와 미분석을 따로 관리한다.
구현·부분구현·불일치 수동 판정에는 근거 청크가 필수이며, 수정 제안은 부분구현·불일치에만 등록한다.
판정 경계의 상세 기준은 [판정 라벨 정의서](label-definition.md)를 따른다.

## 6. 주요 API 연결

다음은 전체 구현 브랜치의 계약이다. `main`에서 아직 연결되지 않은 경로는 기능 상태 조회로 구분한다.
하위 리소스 조회에는 `project_id`가 필요하며 목록은 `{items,total,limit,offset}` 형태다.

| 기능 | 주요 경로 | 현재 계약 |
|---|---|---|
| 프로젝트 | `POST/GET /api/v1/projects` | 등록·조회 |
| 문서 | `POST /api/v1/documents/parse` | multipart `project_id`, `file`; 원문·위치 저장 후 `201` |
| 자동 구조화 | `POST /api/v1/documents/{id}/requirements/extract` | 작업 UUID·`202`·`blocked` |
| 요구사항 | `POST/GET /api/v1/requirements`, `PUT /api/v1/requirements/{id}` | 수동 명세·체크리스트·버전 관리 |
| 체크리스트 생성 | `POST /api/v1/requirements/{id}/checklists/generate` | `202`·`blocked` |
| 코드 입력 | `POST /api/v1/code/index` | `project_id`, `relative_path`; 스냅샷·청크 저장 |
| 검증 | `POST /api/v1/verify/run` | 프로젝트·스냅샷·선택적 요구사항 UUID 목록; `202`·`blocked` |
| 작업 조회 | `GET /api/v1/jobs/{id}`, `GET /api/v1/jobs/{id}/events` | 폴링·SSE |
| 수동 판정 | `POST /api/v1/verification-results/import` | 판정·근거 청크·선택적 제안 저장 |
| 호출 흐름·수정 | `GET /api/v1/requirements/{id}/call-flow`, `GET /api/v1/requirements/{id}/fix` | 흐름 미연결 시 `501`; 등록된 수동 제안 조회 |
| 진단·대시보드 | `GET /api/v1/diagnostics`, `GET /api/v1/projects/{id}/dashboard` | 현재 버전·선택한 스냅샷의 결과 |
| 추적표 | `GET /api/v1/traceability`, `POST /api/v1/traceability/export` | 조회·XLSX |
| 테스트 | `POST /api/v1/test-spec/generate`, `POST/GET /api/v1/test-cases` | 생성 작업은 `blocked`; 수동 관리 |
| 테스트 출력 | `POST /api/v1/test-spec/export` | `project_id`, 선택적 `snapshot_id`; XLSX 바이너리 |
| 모델 설정 | `GET/PUT /api/v1/projects/{id}/llm` | 키를 제외한 단일 설정 |
| 연결 확인 | `POST /api/v1/projects/{id}/llm/connection-check` | 키 요청 계약만 제공, 현재 `501` |

초기 명세의 `/api/spec/parse`, `/api/code/verify`, `/api/test-spec/export`는 호환 경로로 제공한다.
현재 응답은 각각 문서 원문, 검증 작업, XLSX이며 즉시 AI 요구사항·판정·테스트 생성 결과를 제공하지 않는다.
오류는 `{error:{code,message,missing_features}}` 형태로 누락 기능을 명시한다.

## 7. 현재 구현 상태와 남은 작업

전체 구현 브랜치 기준이며, `main` 반영 상태와는 별개다.

| 기능 | 구현된 부분 | 남은 부분 |
|---|---|---|
| 프로젝트·작업 기반 | 등록·조회, 오류 응답, 기능 상태, 작업 폴링·SSE | 실제 실행 워커·재시도 |
| 문서·요구사항 | 텍스트·표·위치 추출, 수동 요구사항·체크리스트, 버전 | OCR·도형·PDF 셀 구조, AI 구조화·분해 |
| 코드 입력 | 스냅샷·청크·라인 저장·조회 | 자동 BE/FE 체크리스트 매칭, TS/TSX/Vue/JSP AST |
| 판정·진단 | 수동 판정·근거·제안, 현재 버전 진단 | AI 매칭·호출 흐름·판정·수정 생성 |
| 테스트·출력 | 수동 케이스, 비고, 실제 XLSX, 대시보드·추적표 | AI 테스트 생성, 고객 양식 세부 서식 |
| 모델 | 단일 설정, 버전 고정, 키 비저장 | 실제 연결 확인·호출, 확장 SecretStorage, 다중 모델 |
| 확장 화면 | 화면 연동에 필요한 REST 조회 데이터 | VS Code UI·코드 이동·수정 적용·MCP 전송 |

Java·JS/JSX·HTML은 기존 AST 청커를 재사용한다. Python은 데코레이터·최상위 문장·함수·클래스를 보존한다.
TS/TSX/Vue/JSP 및 XML/SQL/YAML/properties는 현재 파일 단위로 저장한다.
테스트·빌드·가상환경 디렉터리와 폴더 인덱싱 중 심볼릭 링크는 제외한다.

기본 제한: 문서 20MiB, Office 압축 해제 합계 100MiB, PDF 1,000페이지, Excel 20만 셀, 추출 텍스트 100만자.
코드는 단일 파일 1MiB, 총 30MiB, 3,000개 파일까지며 UTF-8과 허용 워크스페이스 안의 경로만 받는다.

## 8. MVP 검증 및 확장 기준

- 문서 원문·추출 위치, 스냅샷·청크·버전, 수동 판정·테스트·출력을 실제 HTTP 흐름으로 검증한다.
- AI 미연결 요청, 오래된 버전, 다른 프로젝트 참조, 잘못된 경로·형식·용량에 대한 응답을 확인한다.
- 외부 모델을 연결하면 원문 인용·후보 청크·출력 스키마 검증과 판정 정확도·안정성 평가를 추가한다.
- 전체 구현 브랜치의 기존 통합 테스트 29개와 Ruff 검사가 통과했다. 이 결과는 AI 정확도 검증이 아니다.
- 저장소 실행 검증은 SQLite 기준이다. PostgreSQL 실행, 인증, 운영 마이그레이션은 후속 작업이다.
- 후속 다중 모델은 제공자·모델 프로필과 호출 어댑터를 추가하며 공통 업무 로직은 유지한다.
