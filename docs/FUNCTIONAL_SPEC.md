# SpecPilot 기능명세서

버전: 2.2 · 갱신일: 2026-10-10 · 기준: 사용자와 합의한 Figma 개선안

**VS Code 스타일의 독립 웹앱**을 기준으로 한다. 이전의 VS Code 확장·Problems 패널·자동 코드 패치 계획을 대체한다. [API 명세](API_SPEC.md), [모델 개발 담당 명세](MODEL_TEAM_GUIDE.md)와 함께 사용한다.

디자인: [SpecPilot Figma](https://www.figma.com/design/mSOhKOoD64SSxSDtHiB7lR). 디자인의 예시 데이터와 프로토타입 저장 표시는 실제 서버 구현 상태를 의미하지 않는다.

## 1. 목적과 범위

한국어 기획서에서 요구사항을 추출하고, 사람이 원문과 대조해 검토한 요구사항을 고정된 코드 스냅샷과 비교한다. 판정에 근거 코드와 호출 흐름을 붙이고, 테스트 사양서를 생성한다. 실제 시험은 사람이 수행하고 결과를 기록한다.

| 구분 | 범위 |
|---|---|
| MVP 목표 | 프로젝트·문서·코드 등록, 단일 모델 연결, 요구사항 분석·검토·편집, 코드 판정·추적표, 가변 근거 카드, 테스트 생성·절차 편집·실제 결과 입력·Excel 출력 |
| 모델 정책 | 선정한 모델 하나를 문서 구조화·코드 판단·테스트 생성에 공통 사용. 모델 팀원 1·2는 서로 다른 처리 단계 담당 |
| 확장 | 제공자별 모델 어댑터·지원 목록 확대, 추가 포맷·언어, 원격 Git 가져오기, 자동 시험 실행 |
| 제외 | 일본어 번역, VS Code 확장, 자동 코드 수정·커밋, AI 예상 결과를 실제 수행 결과로 기록 |

PDF를 첫 통합 대상으로 한다. DOCX·XLSX·PPTX는 파서가 준비된 포맷만 지원 상태를 켠다. 코드는 Spring/Java·HTML·JavaScript와 React/Express를 우선한다. 미지원 문서·언어를 지원한다고 표시하지 않는다.

모델·제공자는 PoC에서 선정한다. 외부 전송이 제한되는 운영 환경에는 로컬 모델 어댑터가 필요하며, 클라우드 개발 환경과 구분한다.

## 2. 화면 구성과 사용자 흐름

주 메뉴는 **프로젝트 설정 → 명세 분석 → 검증 결과 → 테스트 사양서**다. 별도 홈 대시보드나 두 번째 요구사항 분석 화면을 만들지 않는다. 저장된 프로젝트는 프로젝트 선택 영역에서 연다.

| 디자인 이름 | 역할·진입 |
|---|---|
| `ProjectSetup` / `ProjectSetup_Empty` | 문서·코드·모델 준비 및 등록 전 상태 |
| `RequirementAnalysis` / `RequirementAnalysis_Empty` | 요구사항·수락조건 검토 및 결과 없음 상태 |
| `RequirementAnalysis_SignUp` | 별도 기능 페이지가 아닌 회원가입 요구사항 선택 상태 |
| `DocumentOutlinePanel` | 명세 분석 내부의 원문 목차·페이지 보조 패널 |
| `VerificationResults` / `VerificationResults_Unavailable` | 추적표·통계 및 검증 전·차단 상태 |
| `VerificationDetail` / `VerificationDetail_SignUp` | 추적표에서 선택한 요구사항의 근거·호출 흐름 |
| `CodeEvidenceCard` | 문제/참고 맥락 × 펼침/접힘 변형의 코드 근거 카드 |
| `TestSpecification` / `TestSpecification_Empty` | 시험 목록·예측·수동 수행 기록 및 빈 상태 |
| `TestSpecification_SignUp` | 같은 테스트 화면의 회원가입 선택 상태 |
| `TestSpecification_Editing` / `TestSpecification_SignUp_Editing` | 표 우측 편집 아이콘으로 진입하는 편집 상태; 저장·취소 제공 |
| `SelectedTestExecution` / `SelectedTestExecution_Editing` | 선택한 시험의 실제 결과·메모·상태 조회 또는 편집 영역 |
| `TableCellInput` | 편집 모드의 시험 절차·입력값·기대 결과 입력 셀 |
| `TestProcedureEdit_Reference` / `TestProcedureEdit_SignUp_Reference` | 이전 상세 편집 폼 참고; 현재 기본 흐름에서는 표 편집으로 통합 |
| `TestCaseCreate` | 수동 시험 추가 대화상자 |

1. 프로젝트를 만들거나 연 뒤 문서·모델을 준비한다.
2. 명세 분석을 실행하고 원문 출처·조건을 검토 완료로 확정한다.
3. 코드를 등록·인덱싱하고, 검토된 요구사항 버전과 코드 스냅샷으로 검증한다.
4. 추적표에서 상태·사유를 보고 상세보기에서 여러 코드 위치·호출 관계를 확인한다.
5. 선택한 검증 실행을 기준으로 시험을 생성한다. 표 우측 연필 아이콘으로 편집 모드에 진입한다.
6. 시험 절차 또는 실제 수행 결과를 수정하고 저장으로 확정한다. 취소하면 초안을 폐기한다. 저장된 추적표·사양서를 Excel로 내보낸다.

코드는 설정 단계에서 미리 등록해도 된다. 문서 분석에는 코드가 필요하지 않으며, 코드 검증에는 검토 완료 명세와 준비된 코드 스냅샷이 모두 필요하다.

## 3. 기능별 요구사항

### F01. 프로젝트 설정·모델 연결

- 프로젝트 이름·문서 목록·코드 소스·준비 상태를 표시한다. 문서·코드 등록 위치를 중복 배치하지 않는다.
- **‘이번 분석 범위’ 카드와 ‘저장된 요구사항 열기’ 바로가기를 제거**한다. 검증 항목 설명만 분석 시작 버튼 근처에 짧게 표시한다.
- 모델은 정해진 목록의 드롭다운에서 하나만 고른다. MVP에는 실제 연결된 프로필 하나만 활성화한다. 여러 모델 동시 실행은 제공하지 않는다.
- 확장 프로필은 제공자·모델명·접속 주소·지원 기능을 포함한다. 지원 프로필 선택과 해당 API 키 등록으로 전환한다. 키만 바꿔 미지원 제공자를 자동 인식하지 않는다.
- 키 입력과 연결 확인을 구분한다. 모델·키 변경 후 다시 연결 확인한다. 키 오류·만료·미지원 어댑터를 구분한다.
- 키는 응답·로그·분석 이력·Excel에 넣지 않는다. 지속 저장이 필요하면 백엔드 비밀 저장소 참조를 사용한다. 현재 이 저장소와 실제 연결 검사는 미구현이다.
- 실행 시작 시 모델 설정·프롬프트 버전을 고정한다. 설정 변경은 다음 실행부터 적용한다.

완료 기준: 실제 지원 프로필만 실행 가능하고, 저장된 프로젝트를 열면 서버 상태를 복원한다.

### F02. 문서 등록·파싱·요구사항 추출

- 원본·해시·문서 버전·페이지/시트/슬라이드·텍스트 블록과 출처를 보존한다. 업로드 완료와 분석 완료는 별도 상태다.
- 문서 구조 파싱과 LLM 의미 추출을 분리한다. OCR 필요·읽기 실패·미지원 포맷을 경고로 반환한다.
- **주제 → 소주제 → 요구사항 → 수락조건** 구조를 사용한다. 예: 공지사항 → 공지사항 작성 → 첨부 파일 크기 제한 → 최대 300MB 조건. 주제·소주제 소속과 화면 ID·이름, 요구사항 번호·제목·원문, 조건·동작·기대 결과를 구조화한다. 원문에 없는 기능·업무 규칙·계정을 추가하지 않는다.
- 반복 요구사항은 관계를 연결하거나 계산을 재사용하되 각 화면과 출처를 보존한다. 같은 내용이라는 이유만으로 항목을 삭제하지 않는다.
- 복합 문장은 독립 판정 가능한 **수락조건**으로 분해한다. 조건 수는 내용에 따라 달라지며 예시의 15개 등 고정 수량을 요구하지 않는다.
- 출처가 없거나 모호한 결과는 검토 대상으로 남긴다. 수락조건은 제품 동작의 충족 기준이며 실제 시험 수행 결과가 아니다.

완료 기준: 저장한 요구사항·조건을 원문 블록에서 확인할 수 있고, 읽지 못한 범위와 추출 경고가 드러난다.

### F03. 명세 분석·검토·편집

- 목록과 선택 항목 상세를 한 화면에서 제공한다. 목록은 주제·소주제로 묶어 펼치고 접으며, 선택 경로를 `공지사항 / 공지사항 작성`으로 표시한다. 원문 목차는 보조 패널로 연다.
- 기능 주제·소주제는 탐색용 계층이고 조건 분류·화면 연결과 별도다. 소속이 불확실하면 미분류로 표시하고 검토 사유를 보여준다. 출력 계약은 [팀원 1 안내](PARSER_OUTPUT_SPEC.md)를 따른다.
- 표시 분류는 **입력값 검증·경로 및 이동·비즈니스 로직·데이터 저장·오류 메시지**다. 조건마다 하나의 주 분류와 관련 조건 ID를 지정한다.
- 프런트엔드/백엔드/양쪽/미정 대상, 기능/비기능 유형, 정적 검증 가능 여부를 별도 필드로 둔다. 원문에 없는 서버 검증을 임의로 추가하지 않는다.
- 제목·조건·동작·기대 결과·하위 조건을 편집한다. 추출 원문은 보존하고 수정 시 새 버전과 이력을 만든다.
- **명세 검토 상태와 코드 구현 상태를 분리**한다. 검토 완료는 구현 완료가 아니다.
- 수정 시 기존 검증을 과거 버전으로 표시하고 재검증 필요를 알린다. 과거 결과는 지우지 않는다.

완료 기준: 선택한 검토 완료 버전만 검증 실행에 고정한다. 검토 전 항목을 조용히 포함하지 않는다.

### F04. 코드 등록·스냅샷·호출 범위

- 현행 로컬 개발 API는 서버의 허용 워크스페이스 경로를 사용한다. 웹 파일 업로드에는 ZIP 가져오기가 추가로 필요하다. 원격 Git 가져오기는 후속 개발이다.
- 함수·메서드·템플릿·설정 등을 청크로 저장한다. 경로·줄 번호·원문은 파서가 확정하고 LLM은 기존 청크 ID를 선택한다.
- 코드 해시·스냅샷을 고정한다. 재등록으로 과거 분석 근거가 현재 코드로 바뀌면 안 된다.
- 진입점과 호출 관계를 추출하고 해당 화면 도달/다른 화면/도달 불가 범위를 구분한다.
- 동적 호출·설정 누락·미지원 스택을 표시한다. 관계를 못 찾았다는 이유만으로 기능 부재를 단정하지 않는다.

완료 기준: 모든 근거를 해당 실행 스냅샷에서 다시 열 수 있고 과거 결과가 보존된다.

### F05. 코드 정합성 검증·추적표

조건별 판정 후 요구사항 단위로 집계한다. [판정 라벨 정의](label-definition.md)와 `verdict/rules.py`를 현재 적용 기준으로 삼되, 문구 차이·서버 검증 부재의 세부 정책은 발주사 확인 전 잠정 기준임을 유지한다.

| 상태 | 표시·의미 |
|---|---|
| `implemented` | 구현됨: 충족하는 코드 근거 있음 |
| `partial` | 부분 구현: 일부 충족·일부 누락 |
| `mismatch` | 불일치: 구현된 값·동작 등이 명세와 다름 |
| `not_found` | 미구현 후보: 분석 범위에서 관련 구현을 찾지 못함 |
| `needs_review` | 확인 필요: 근거·범위·동적 값 등이 불충분 |
| `not_statically_verifiable` | 정적 검증 불가: 실행 화면·환경 확인 필요 |
| `null` | 미분석: 판정 실행 없음 |

- 상태·명세 기준·코드 동작·차이·근거 ID·범위·경고를 반환한다. 문구 일치·서버 검증 위험·명세 의심 사유는 별도 보조 필드다.
- 추적표 열: 요구사항 ID·기능명·상태·관련 코드·사유·상세보기. 검색·상태 필터·Excel 출력 제공.
- 구현율 = 구현됨 요구사항 수 / 선택 범위 전체 요구사항 수 × 100. 미분석·정적 검증 불가도 분모에 포함한다. 전체 0건이면 0%. 다른 분모의 비율은 이름과 분모를 별도로 표시한다.
- 동일 원인은 문제 ID로 묶는다. **문제 수·영향 조건 수·근거 위치 수·파일 수**를 구분한다.
- 집계 시 정적 검증 불가를 제외하고 불일치 → 확인 필요 순으로 우선한다. 나머지가 전부 구현이면 구현됨, 전부 미발견이면 미구현 후보, 섞이면 부분 구현이다. 전부 정적 검증 불가이면 해당 상태, 조건이 없으면 확인 필요다. 미판정 조건이 있으면 완료 집계를 표시하지 않는다.

완료 기준: 비슷한 이름의 코드만으로 구현됨을 반환하지 않는다. 다른 화면 근거만 있으면 확인 필요로 남긴다.

### F06. 검증 상세·가변 코드 근거

- 요구사항·수락조건·문제 요약·호출 흐름·근거 목록을 함께 표시한다.
- 근거 카드는 **0..N개**다. 각각 파일·줄 범위·코드·문제 또는 참고 역할·사유·관련 조건·선택적 수정 제안을 포함한다.
- 첫 문제 카드를 펼치고 나머지는 접는다. 개별 펼침/접힘·유연한 높이·목록 세로 스크롤로 여러 위치를 다룬다.
- 호출 노드 선택 시 관련 카드를 선택한다. 문제가 있는 단계만 강조한다. 노드와 카드 수는 같을 필요가 없다.
- 근거 0개이면 검색 범위·검토 또는 미발견 사유를 표시한다. 가짜 코드·수정 제안을 채우지 않는다.
- 수정 제안은 사람이 검토할 텍스트이며 자동 적용하지 않는다.

예: 크기 제한 오류 한 건이 검사·오류 메시지 두 조건에 영향을 주고, 서비스 두 위치와 컨트롤러 참고 위치까지 세 카드로 나타날 수 있다.

완료 기준: 0개·1개·다수 근거를 같은 데이터 구조로 표시하고 파일 수와 위치 수를 혼동하지 않는다.

### F07. 테스트 생성·시험 절차 편집

- 검토된 요구사항 버전과 선택한 검증 실행에서 정상·오류·경계 시험을 생성한다. 계정·환경이 없으면 사용자 준비 필요로 표시한다.
- 요구사항·조건 ID, 전제·입력·순서 있는 절차·기대 결과·출처·버전을 기록한다.
- 코드 예상 결과는 정상 예상·실패 예상·확인 필요·미예측으로 표시한다. 실제 수행 상태와 별도 열이다.
- 시험 추가 폼은 전제·입력·절차·기대 결과를 받는다. 기존 시험의 절차·입력·기대 결과는 표 편집 모드에서 수정한다. 별도의 시험절차 편집 버튼을 기본 화면에 중복 배치하지 않는다.
- Test ID·코드 기반 예상 결과는 읽기 전용이다. 사람이 절차·입력·기대 결과를 바꾸면 이전 예측을 그대로 적용하지 않고 갱신 필요로 표시한다.
- 재생성은 새 후보를 만든다. 사람이 편집한 절차와 이전 수행 결과를 덮어쓰지 않는다. 채택한 변경은 새 사양서 버전이 된다.

완료 기준: 각 시험이 어느 요구사항·수락조건을 검증하는지 추적 가능하다. 추측한 기대 결과·계정은 사실처럼 저장하지 않는다.

### F08. 표 편집 모드·명시적 저장

- 기본 화면은 읽기 전용이다. 표 우측 상단의 연필 아이콘을 누른 경우에만 시험 절차·입력값·기대 결과와 선택한 시험의 실제 결과·메모·수행 상태를 편집한다.
- 편집 모드에서는 같은 위치에 **저장 버튼 하나와 취소 버튼**을 제공한다. 입력·포커스 이탈·상태 선택만으로 서버 저장이나 집계 갱신을 하지 않는다.
- 수행 상태는 미실행·통과·실패·보류다. 생성 직후 모두 미실행이며 AI의 실패 예상으로 실제 실패를 기록하지 않는다.
- 목록은 선택 행·시험 ID를 표시하고 스크롤한다. 행을 이동해도 시험별 초안을 보존한다. 미저장 상태로 화면을 나가면 저장·변경 폐기·계속 편집 중 선택하도록 한다.
- 저장은 변경된 항목만 함께 반영한다. 성공하면 읽기 모드로 돌아가 저장됨을 표시하고 목록·집계를 서버 값으로 갱신한다. 변경이 없으면 저장을 비활성화한다.
- 취소는 해당 편집 세션의 초안을 폐기하고 기존 저장값을 복원한다. 저장 요청을 보내지 않는다.
- 필드 오류·네트워크 실패·버전 충돌이면 읽기 모드로 전환하지 않는다. 입력을 보존하고 문제 항목·재시도를 제공한다. 배치 중 일부만 저장하는 상태를 만들지 않는다.
- 저장 중에는 중복 제출·취소·이탈을 막고 진행 상태를 표시한다. 동시 수정은 버전 충돌로 알리며 최신값을 무조건 덮어쓰지 않는다.
- 절차 버전과 수행 회차는 구분한다. 수정된 절차의 수행 결과는 새 회차로 저장하고 이전 절차·수행 기록을 유지한다. 실제 시험한 빌드·환경을 기록할 수 있다.

완료 기준: 편집·취소만으로 저장 데이터가 바뀌지 않는다. 저장 성공 후 새로고침하면 결과가 복원된다. 실패·충돌 시 모든 변경을 보존하고 일부 저장을 하지 않는다. Figma의 상태 이동·예시 입력은 실제 서버 저장 구현과 구분한다. 자동 시험 실행기는 후속 개발이다.

### F09. 작업 상태·내보내기

- 긴 작업은 작업 ID를 반환하고 폴링/SSE로 진행·완료·실패 사유를 제공한다.
- AI 미연결은 차단 상태와 필요한 기능을 반환한다. 성공·더미 결과로 위장하지 않는다.
- 추적표 출력: 출처·조건·판정·근거·스냅샷·모델 버전. 시험 출력: 절차·기대 결과·코드 예측·실제 상태·실제 결과·메모를 각각 다른 열로 기록한다.
- 지정한 실행·사양서 버전·수행 회차를 내보내며 현재·과거 버전을 조용히 섞지 않는다.
- 빈 결과·미지원 파일·연결 실패·미검토·근거 없음·저장 충돌·다운로드 실패를 안내한다.

## 4. 현재 구현 상태

확인 기준: 2026-10-10, 현재 체크아웃 `docs/functional-specification`, 커밋 `b3d1a76`. 다른 기능 브랜치와 합쳐진 것으로 가정하지 않는다. [API 명세의 구현 현황](API_SPEC.md#2-현재-api와-기능-브랜치)을 함께 확인한다.

| 기능 | 확인 상태 | 추가 개발 |
|---|---|---|
| FastAPI·프로젝트 등록/조회·기능 상태 | 현재 HTTP 연결됨 | 화면 연결 |
| 작업 조회·폴링/SSE 기반 | 현재 HTTP 연결됨, AI 워커 완성 아님 | 실제 실행·진행 이벤트·재연결 |
| 문서 파싱·조건 분해 | 기존 CLI 샘플 파서·LLM 로직 있음 | 일반 문서·출처 계약·HTTP 연결 |
| 코드 청킹·매칭·범위·판정 | 기존 CLI 로직 있음 | 프로젝트별 어댑터·불변 이력·HTTP 연결 |
| 문서·코드·요구사항·수동 판정·시험·출력·LLM 설정 API | 누적 기능 브랜치 `feat/llm-settings-api`에 기반 코드 있음 | 병합 상태 확인·새 계약 반영·AI 연결 |
| 모델 드롭다운·가변 근거·호출 흐름 | Figma 디자인, DTO 일부 있음 | 웹 UI·문제/근거/노드 연결 계약 |
| 테스트 자동 생성 | 기존 CLI에도 미구현 | 팀원 2 생성기·출력 검증·HTTP 연결 |
| 표 편집·명시적 저장 | Figma 디자인·프로토타입 | 배치 저장 API·수행 회차·충돌 처리·웹 UI |
| Excel | CLI 추적표 및 기능 브랜치 출력 기반 있음 | 새 조건·시험·수행 회차 계약 연결 |

이 문서 갱신은 구현 완료 보고가 아니다. 기능 브랜치를 통합해도 새 UI 계약·모델 연결은 별도로 검증해야 한다.

## 5. 공통 완료 조건

- 원문 → 요구사항 → 수락조건 → 판정 → 코드 근거 → 시험 → 수행 결과가 ID로 연결된다.
- 문서 해시·요구사항 버전·코드 스냅샷·모델 설정·프롬프트 버전을 기록한다.
- 명세 검토·코드 판정·시험 예측·실제 수행·저장 상태를 서로 다른 상태로 표현한다.
- 미지원·미연결 기능은 사유를 제공하고, 과거 기록·사용자 편집은 보존한다.
- 화면·API·모델 담당 문서의 필드와 enum을 함께 관리한다.
